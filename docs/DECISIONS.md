# 决策记录

记录已经做出的决定、原因和被否决的方案，防止新会话重复讨论或重新提出已否决的方案。

**规则**：

- 只追加，不删除。决定被推翻时，新增一条记录说明，并在旧记录的状态中注明"已被 D-xxx 取代"。
- 状态分为两种：
  - **已确认**：用户已同意，按此实现。
  - **提议**：设计时补充的细节，尚未经用户逐条确认。实现到相关任务时先向用户说明并确认，确认后改为"已确认"。

## 已确认

### D-001 没有 Web 界面，使用数字菜单的命令行工具

- **原因**：目标是轻量，Web 面板常驻占用内存，暴露额外端口也增加风险。菜单风格参考 3x-ui 的命令行菜单。

### D-002 使用 Go 开发，编译为单个二进制文件

- **原因**：零依赖，JSON 处理、二维码、密钥生成都在程序内完成；运行时不常驻，内存占用不是问题；编译 amd64 和 arm64 两个版本即可覆盖绝大多数 VPS。
- **否决**：Bash 脚本。需要 jq、qrencode 等依赖，分享链接、状态文件、SSH 互锁检查等逻辑用 Bash 难以维护。

### D-003 防火墙和端口转发统一使用 nftables

- **原因**：ufw 依赖 Python，精简镜像需额外安装几十 MB；ufw 默认丢弃转发流量，与 nftables 端口转发同时使用需要处理规则冲突。统一用一张 nftables 表更简单、更轻。
- **否决**：ufw。
- **代价**：用户不能用 `ufw` 命令手动管理规则，只能通过菜单或 `nft`。
- **补充**：用户自己在运行 ufw 时，LiteNode 防火墙未启用期间把端口同步到 ufw，见 D-038。本条不变：LiteNode 自己的防火墙和端口转发仍只用 nftables，不安装、不依赖 ufw。

### D-004 不做 fail2ban

- **原因**：依赖 Python 且常驻内存，占用可能超过 Xray；"仅密钥登录 + 修改端口"后暴力破解已无意义。

### D-005 中转只做 nftables 端口转发

- **原因**：链式代理（导入落地机、链式出站、路由规则）在 3x-ui 的 Web 界面中操作更方便，命令行菜单没有优势。纯端口转发零开销，线路机可以不装 Xray。
- **否决**：链式代理出站、出站与路由规则管理。

### D-006 不做快速部署向导

- **原因**：用户认为没有必要。

### D-007 第一版不做流量统计、流量限额、到期停用

- **原因**：需要开启 Xray stats API 并有定时任务持续统计和持久化，增加复杂度。端口转发同样不做流量统计。以后需要时再讨论。

### D-008 不引用 geoip / geosite，没有"更新 geo 数据"功能

- **原因**：Xray 引用 geo 文件时会加载到内存，显著增加占用。节点不需要分流规则，屏蔽内网地址直接写 IP 段。

### D-009 Xray 配置最小化

- **内容**：不开启 stats 和 API，不开启访问日志，只保留 warning 级别日志，出站只有 freedom 和 blackhole。
- **例外**：Reality 回落限速默认开启（见 D-018），它是安全功能且不增加内存占用。

### D-010 第一版只支持 Debian 和 Ubuntu

- **原因**：Alpine 等使用 OpenRC 而不是 systemd，服务管理方式完全不同。核心功能稳定后再考虑。

### D-011 项目名 LiteNode，命令 `litenode` 和 `lnode`

- **原因**：名字表达"轻量"；代理领域没有同名项目（同名项目在 Node.js、Python 等其他领域）。
- **否决**：NodeKit（Algorand 有一个同样是"终端管理节点 + 一行命令安装"的同名工具，容易混淆）；命令名 `node`（与 Node.js 冲突）、`ln`（系统自带命令）、`lnd`（闪电网络常用程序）。

### D-012 开源协议 GPL-3.0

- **原因**：防止被闭源二次打包售卖；与 3x-ui 一致。Xray 是运行时下载的独立程序，其协议不影响本项目。

### D-013 安装方式：一行命令执行 install.sh，从 GitHub Releases 下载程序

- **原因**：与 3x-ui 的安装体验一致，是新 VPS 上最方便的方式。之后可用自己的域名做短链接，程序无需改动。
- **否决**：apt 软件源（首次安装步骤更多）、Docker（守护进程常驻内存）。
- **补充**：之后的更新通过"维护 → 更新脚本"完成。

### D-014 菜单排序和分隔线规则

- **选项顺序**：添加 → 修改 → 启用/禁用 → 其他操作 → 删除和危险操作 → 返回。
- **分隔线**：子菜单的选项区内不加分隔线，唯一的分隔线在 `0. 返回` 上方。删除和危险操作放在最后，但不用分隔线隔开。
- **主菜单例外**：主菜单的分组分隔线已由用户确认保留。
- **原因**：用户明确要求。曾经出现过"分享链接排第二""删除排在中间""在危险操作上方加分隔线"等问题，均被用户否决。

### D-015 节点结构：协议 + 传输 + 安全层，编译时注册

- **原因**：后续要支持纯 VLESS、XHTTP、WS 等多种组合，组合式结构让新增一种传输或协议时所有兼容的组合都能直接使用。菜单只展示预设组合，保持简单。
- **否决**：Go 运行时插件（版本稍有不匹配就无法加载）；每种组合写一个独立类型（组合数量爆炸）。

### D-016 Reality 目标网站：检测必做，扫描为推荐选项

- **内容**：所有选定的目标网站都必须通过 TLS 1.3、H2、X25519、证书检测。提供"扫描附近网站 / 常用列表 / 手动输入"三种方式。
- **扫描限制**：默认只扫同一 /24 网段的 443 端口，低并发，首次使用时提示部分商家禁止扫描。
- **原因**：目标不满足要求时节点连不上；用大站存在 IP 与 SNI 不匹配被识别的风险；同机房的网站更自然。

### D-017 第一版不做"偷自己"

- **原因**：需要域名、证书和 Web 服务，与轻量目标冲突。

### D-018 防止流量偷跑：筛选排除高风险网站 + 默认开启回落限速

- **原因**：Reality 会把未通过验证的连接转发给目标网站，别人可以把 VPS 当作访问目标网站的免费中转。
- **内容**：排除 cdn、download、mirror、video 等关键词的网站；`limitFallbackUpload` / `limitFallbackDownload` 默认采用官方示例值（10MB 后开始限速，1MB/s，突发 5MB/s）。
- **否决**：前置 Nginx 过滤 SNI（需要额外的 Web 服务）。

### D-019 卸载时不回滚 SSH 和防火墙设置

- **原因**：避免卸载后机器恢复成密码登录、端口全开的不安全状态。

### D-020 卸载 Xray 时同时删除所有节点和客户端

- **原因**：卸载后保留节点配置的唯一用途是重装，而重装、换版本、修复已由"更新 Xray（可选指定版本）"覆盖。单独卸载 Xray 的真实场景是落地机改成纯线路机。

### D-021 开发环境：WSL（Ubuntu）+ 测试 VPS（Debian 12），不另建虚拟机

- **内容**：WSL 用于开发、编译、单元测试；测试 VPS 用于验证 SSH、nftables、BBR、swap 和实际连接。测试 VPS 有 VNC 控制台，可随时重装。仓库放在 WSL 主目录，Claude Code 在 WSL 环境中运行。

### D-022 提交和 PR 中不出现 AI 署名

- **内容**：`.claude/settings.json` 中 `attribution.commit` 和 `attribution.pr` 设为空字符串，`CLAUDE.md` 中同时写明规则。

### D-023 暂不配置 GitHub Rulesets

- **状态**：已被 D-036 取代。
- **原因**：单人开发，要求 PR 或检查会增加步骤。用户可以自行添加"禁止删除 main、禁止强制推送"的基础规则。

### D-024 进度衔接方式：仓库内的文档是唯一记忆

- **内容**：`CLAUDE.md`（工作规则）、`docs/DESIGN.md`、`docs/DECISIONS.md`、`docs/ROADMAP.md`、`docs/PROGRESS.md`。任务带编号和验收标准，提交信息带任务编号。
- **分工**：Claude Code（WSL）负责具体实现；claude.ai 对话负责方案指导，新对话时直接读取仓库文件衔接。

### D-025 界面文字集中管理在 `internal/text`

- **内容**：所有用户可见的文字（菜单、提示、确认、错误信息）只写在 `internal/text`，用 Go 函数或常量定义；第一版只有中文，不做运行时语言切换。`fmt.Errorf` 包装的上下文用英文。单元测试扫描其他包的非测试 Go 文件，出现中文字符串即失败（与 `text` 包同时实现）。
- **原因**：为以后支持英文做准备，现在还没有界面文字，集中管理几乎没有迁移成本，事后补做需要改动所有功能代码；同时保证用词统一、逻辑层测试不依赖具体措辞。
- **否决**：JSON / YAML 翻译文件、第三方 i18n 库（失去编译期检查，增加依赖）；文字分散写在各包中（以后支持英文的返工成本最高）。
- **代价**：读代码时需要跳转到 `text` 包才能看到实际文字；每条文字多一处定义。

### D-026 dry-run 只读操作照常执行；操作日志只记录修改操作，1MB 轮转

- **内容**：Runner 区分只读和修改操作，dry-run 下只读操作真实执行、修改操作只打印。`/var/log/litenode.log` 只记录修改操作，超过 1MB 轮转为 `.1`，最多约 2MB。
- **原因**：dry-run 需要基于真实状态才有参考价值；只读查询每次打开菜单都会执行，记录会刷满日志；自行轮转不依赖精简镜像中可能没有的 logrotate。
- **否决**：dry-run 下所有操作都不执行（菜单状态失真）；记录查询操作；交给 logrotate；不控制日志大小。

### D-027 系统检测细节：版本边界、虚拟化显示、共存软件提示

- **状态**："共存软件"一项已被 D-037 取代，其余（版本边界、虚拟化类型显示）不变。
- **版本边界**：下限固定、上限开放（Debian ≥ 11；Ubuntu ≥ 22.04 且为 LTS），拒绝 Ubuntu 非 LTS、Debian testing/sid、衍生发行版。
- **虚拟化类型**：显示在主菜单系统行，如 `Debian 12 | KVM | 512M | BBR ✓`。
- **共存软件**（x-ui/3x-ui、官方 xray、Docker）：按 systemd 单元文件检测，在主菜单状态区下方显示一行警告，不打断操作。x-ui 和 3x-ui 合并显示。
- **原因**：新的 Debian 和 Ubuntu LTS 发布后不需要更新 LiteNode 才能使用；容器环境一眼可见；警告不打断日常使用。
- **否决**：严格版本白名单；虚拟化类型不显示；启动时打印警告并要求按回车；尝试区分 x-ui 和 3x-ui（依赖上游特征，容易失效）。

### D-028 状态文件：字段随任务加入、菜单会话全程持锁、异常时提示不覆盖

- **字段**：M0-04 只做顶层骨架，功能字段在对应任务加入。只有不兼容的改动才加 `schema_version`，v0.1.0 前保持 1。
- **锁**：`flock /run/litenode.lock`，菜单会话全程持有；`internal rollback` 不受锁限制，`internal resolve` 遇锁跳过本轮。
- **异常**：文件损坏或版本比程序新时提示并退出，不自动覆盖、不自动从备份恢复；文件不存在视为首次使用。
- **原因**：一次写全结构容易与后续任务的细化不一致；只在写入时加锁会让两个菜单互相覆盖修改；自动恢复会悄悄丢掉最近的修改。
- **否决**：现在定义完整结构；只在写入状态时加锁；损坏时自动用最近的备份恢复。

### D-029 配置变更流程的实现方式

- **状态**：确认竞态的标记和定时任务"按类型各一个"已被 D-040 取代（改为全局一个，整体回滚一次变更）；其余不变。
- **备份**：每次变更一个目录，原样保存文件 + `state.json` + `manifest.json`，用户可直接复制恢复。
- **校验**：默认在临时位置校验；`sshd` 这类只能校验正式位置的，就地校验、失败立即恢复（服务尚未重载）。
- **确认竞态**：确认和超时回滚通过 rename 认领 `/run/litenode/<类型>.pending` 标记文件，先到者生效；回滚恢复标记中记录的备份 ID，而不是"最新一份"。
- **原因**：与 D-028 中"手动从备份恢复"的提示一致；不必要地改动正式文件越少越好；rename 是原子操作，保证"保留"和"回滚"只发生一个。
- **否决**：JSON 打包备份（无法直接复制恢复）；一律写入后校验；确认时如果已超时仍重新应用新配置（此时已没有回滚保护）。

### D-030 菜单框架细节

- **内容**：选项统一缩进 1 个空格（主菜单示例同步修改）；不清屏；状态区未实现的模块显示 `-`；执行操作时收到 Ctrl+C / SIGHUP / SIGTERM 等操作完成后再退出，等待输入时立即退出。
- **原因**：缩进与状态区、子菜单一致；不清屏可以往上翻看之前的输出；布局从一开始与设计一致；SSH 断开或误按 Ctrl+C 不会让配置停在修改一半的状态。
- **否决**：主菜单 2 格、子菜单 1 格；清屏并要求"按回车继续"；只显示系统行；操作中立即退出。

### D-031 子命令细节

- **内容**：`--dry-run` 要求 root，与正常模式走相同流程；支持 `-v` / `--version` / `-h` / `--help`；`version`、`help` 不需要 root。
- **原因**：dry-run 读到的状态和锁与真实运行一致，预览才可信（在 WSL 中用 `sudo litenode --dry-run`，dry-run 不修改系统）；短写法符合命令行工具习惯。
- **否决**：dry-run 不要求 root（读不到状态文件、拿不到锁，需要大量特殊处理）；只支持 `version` 和 `help`。

### D-032 CI 和发布只用 GitHub 官方 Action + gh CLI；v0.0.1 保留为正式 Release

- **内容**：`actions/checkout`、`actions/setup-go` 按 commit SHA 固定；发布用 `gh release create`，说明取自标签注释。测试标签 `v0.0.1`（开发中测试版）保留为正式 Release。
- **原因**：与"依赖尽量少"的原则一致，固定 SHA 防止 Action 被篡改；install.sh 从 `releases/latest` 下载，预发布版不算 latest，保留 v0.0.1 正好用于 M0-09 在测试机上验证安装。
- **否决**：第三方发布 Action（softprops/action-gh-release、goreleaser）；测试标签标记为预发布版或验收后删除。

### D-033 install.sh 的重复安装和 lnode 冲突

- **内容**：再次运行时用最新版覆盖程序；`lnode` 被其他程序占用时不覆盖，提示后继续。
- **原因**：安装脚本可以兼作"修复/重装程序"，校验失败时旧程序保持不变；不破坏用户已有的其他程序。
- **否决**：已安装时直接进入菜单（程序损坏时无法用安装脚本修复）；`lnode` 冲突时中止安装或覆盖。

### D-034 `/etc/litenode` 下的权限统一显式设置

- **内容**：`/etc/litenode` 711，其下子目录 700、文件 600（包括备份中的 `xray.json` 副本、`nftables.nft`、校验用临时文件），唯一例外是 `/etc/litenode/xray.json` 640 属组 `litenode-xray`。规则集中定义在 `internal/state/layout.go`，所有目录用 `EnsureDir`（创建后显式 chmod），配置变更流程拒绝不符合规则的文件。由测试检查除 `xray.json` 外没有任何文件对 root 以外的用户可读。
- **原因**：用户补充要求（P-002 把 `/etc/litenode` 改为 711 后，不能依赖默认权限，备份里有私钥）。
- **实现中发现**：备份恢复 `xray.json` 时原先会丢失属组，导致 Xray 读不到配置；已在备份中记录属组并在恢复时还原。

### D-035 Xray 安装细节：没有节点时不运行；用集成测试在测试 VPS 上验证

- **补充**：用户手动停止 Xray 的处理见 D-045。
- **内容**：安装只装程序、用户和服务文件，不启动；没有启用的节点时 Xray 停止并取消开机启动。M1-01 的 [VPS] 验收用带 `vps` 构建标签的集成测试（`internal/xray/vps_test.go`）在测试机上执行，正常 `go test` 不包含它。
- **原因**：轻量原则，空跑的 Xray 白占内存；M1-01 没有菜单入口，集成测试不需要为验证增加产品功能。
- **否决**：用空配置一直运行；把 [VPS] 验收推迟到 M1-09。

### D-036 使用分支开发，PR squash 合并，main 受 Ruleset 保护

- **内容**：每个任务一个分支（`<type>/<任务编号>-<英文简述>`），验收通过后开 PR，CI 通过且用户在对话中确认后由 Claude 用 `gh pr merge --squash --delete-branch` 合并。main 用 GitHub Ruleset 保护：必须经过 PR、CI（`test` 任务）通过、禁止强制推送和删除，不要求审批人数，没有绕过名单。仓库只允许 squash 合并，合并后自动删除分支。
- **原因**：install.sh 直接从 main 下载，main 必须始终可用，CI 和测试机验证应在合入 main 之前完成；进行中的提交可以随时推送到远程分支备份；每个任务一个 PR，便于审阅和整体撤回。分支上的操作由 Claude 完成，用户只需确认合并。
- **取代**：D-023（理由"要求 PR 会增加步骤"在改用 PR 后不再成立）。
- **否决**：继续直接提交到 main；一个里程碑一个分支（PR 过大）；merge commit / rebase 合并（main 上提交过多）；用户在网页上合并；只禁止强推和删除、不要求 PR。

### D-037 不按软件名检测共存程序，端口冲突以实际占用为准

- **内容**：删除启动时对 3x-ui、x-ui、官方 xray 的检测和主菜单提示。所有端口冲突检查（节点、转发、SSH、导入）都看系统中实际在监听的端口（读 `/proc/net`，不管是哪个程序，包括只监听 127.0.0.1 的）以及状态文件中登记的端口（包括已禁用的节点和转发，因为 DNAT 不监听端口）；TCP / UDP 分开判断，端口段逐个检查，修改时排除自身，启用已禁用项和导入时也检查。Docker 只在启用 LiteNode 防火墙时提示。
- **原因**：按软件名检测既不完整（其他面板、手动安装的程序检测不到）也不准确（装了不代表占用了端口）；端口是否可用才是真正需要判断的事。
- **取代**：D-027 中的"共存软件"一项。已实现的代码由 M0-10 移除。
- **否决**：只检查监听端口（看不到 DNAT 转发占用的端口，会让转发悄悄截走其他程序的流量）。

### D-038 ufw 在运行且 LiteNode 防火墙未启用时，把 LiteNode 管理的端口同步到 ufw

- **内容**：节点端口（`ufw allow`）、转发规则（`ufw route allow` 到 DNAT 后的目标 IP 和端口）、SSH 端口（修改端口时）自动同步到 ufw，规则带备注 `litenode:<类型>:<ID>`，只增删带标记的规则。添加前若已有等价的未标记用户规则，则不添加、不打标记、不删除（ufw 判断重复时不看备注，会把用户规则改成带标记）。同步采用整体对账：根据状态文件算出应有规则，与实际带标记规则比较，多删少补；在每次相关变更、转发目标重新解析、导入配置、打开主菜单时进行。SSH 修改端口时先放行新端口，超时回滚后通过对账删除；旧端口的用户规则经用户同意才删除。卸载 Xray 删除节点规则；全部卸载删除节点和转发规则、保留 SSH 规则；卸载脚本保留全部。启用 LiteNode 防火墙时提示先停用 ufw，停用后删除带标记的 ufw 规则；两者同时启用时主菜单警告。firewalld 不同步。
- **与 D-003 的关系**：D-003 决定 LiteNode **自己的**防火墙和端口转发只用 nftables、不依赖 ufw，本条不改变这一点：LiteNode 不安装、不启用、不停用 ufw，nftables 规则照常生成。本条只处理"用户自己在用 ufw"这种共存情况，让 ufw 不挡住 LiteNode 的节点和转发。D-003 的代价"用户不能用 ufw 管理规则"因此只在启用 LiteNode 防火墙后成立。
- **原因**：很多 VPS 用户已经在用 ufw，不同步的话新加的节点和转发会被 ufw 挡住，用户难以排查；只动带标记的规则，不破坏用户已有的配置；整体对账让超时回滚、后启用 ufw、同步中途失败都能自动恢复一致。
- **实现**：通用模块在 M1-07a，节点在 M1-07，SSH 在 M2-05，转发在 M4-01 / M4-02，卸载在 M1-09 / M6-03，导入在 M6-01，与 LiteNode 防火墙的切换在 M3-02。
- **否决**：逐条增删（超时回滚在另一个进程中执行，无法知道要删哪条）；同步 firewalld；自动停用 ufw。

### D-039 节点模型：组件参数用带类型的可选字段，显式注册，备注规则

- **组件参数**：每个组件一个带类型的可选字段（如 `reality`），JSON 与 DESIGN 第 5 节一致，编译期类型检查。代价：新增组件时要在节点结构中加一个字段（新增字段不加 `schema_version`）。
- **注册**：在 `internal/node/builtin` 中显式注册组件、兼容性表和预设，不使用 `init()` 副作用；组件接口先只有 `Name()` / `Label()`，生成配置和链接的方法由 M1-03、M1-06 加入。
- **备注**：节点备注在节点之间唯一；客户端备注（Xray 的 email）在所有节点的所有客户端之间唯一；两类备注互不影响，第一个客户端默认用节点备注。格式为去掉首尾空白后 1～32 个字符、不含控制字符，比较不区分大小写。
- **原因**：类型检查比通用 JSON 更不容易出错，且状态文件与设计文档一致；显式注册一眼能看出有哪些组件；客户端备注作为 email 必须全局唯一，节点备注只用于显示，分开管理第一个客户端才能默认沿用节点备注；长度限制保证菜单对齐，不区分大小写避免看起来相同的两个备注。
- **否决**：通用的"组件名 → 原始 JSON"（需改 DESIGN 第 5 节，失去类型检查）；节点和客户端备注共用命名空间；只允许字母数字（不能用中文）；只要非空即可。

### D-040 一次变更包含多类配置，整体备份、校验、应用和回滚

- **内容**：变更流程从"一次一类配置"扩展为"一次变更包含多类配置"：一份备份，先全部校验，再按顺序写入、保存状态、依次应用；任何一步失败恢复全部文件和状态并按顺序重新应用旧配置。没有文件、只有"应用"的类型（如 ufw 对账）也可参加。限时确认的定时任务和标记改为全局一个（`litenode-rollback`、`/run/litenode/pending`），`internal rollback` 不再带类型参数，超时时整体回滚。一份备份在其涉及的每一类中各算一份，在每一类中都不属于最新 10 份时才删除。由新任务 M1-00 在 M1-03 之前修改 M0-05 的代码。

- **否决**：保持单类、各功能自己写撤销逻辑（容易漏，超时回滚时更难处理）；保持单类、接受部分生效。

### D-046 端口转发按地址族分别转发

- **内容**：nftables DNAT 不能跨地址族，IPv4 连接只转发到 IPv4 目标、IPv6 连接只转发到 IPv6 目标。目标为 IP 时只转发同一地址族并在列表中标明；目标为域名时分别解析 A / AAAA（`resolved_ipv4` / `resolved_ipv6`，取代原来的 `resolved_ip`），各自转发，ufw 的 `route` 规则也分别生成。存在 IPv6 目标时才开启 IPv6 转发。转发尚未实现，不需要迁移。
- **原因**：两种地址都用时 IPv4 和 IPv6 客户端都能使用，且不需要用户额外选择。
- **否决**：域名只用 IPv4 地址；每条规则由用户选择。

### D-047 x25519 密钥的验收方式；Xray 新特性第一版不做

- **内容**：Xray v26 的 `xray x25519` 输出为 `PrivateKey` / `Password (PublicKey)` / `Hash32`，编码仍是 43 个字符的 base64url。M1-04 的单元测试用真实输出作为测试向量（私钥推导出的公钥必须逐字一致），测试 VPS 上用 `xray x25519 -i <私钥>` 交叉验证。状态文件仍为 `public_key`，分享链接仍为 `pbk`。VLESS Encryption（ML-KEM-768 / `vlessenc`）、REALITY 的 ML-DSA-65、`Hash32` 第一版不做。
- **原因**：原验收"格式与 xray x25519 输出一致"在新版本下含义不明；这些新特性是可选增强，现有 VLESS + REALITY 不需要，且许多客户端尚未支持。以后可作为预设或高级选项讨论。

### D-049 Xray 路由阻断内网时也拦截域名

- **内容**：路由 `domainStrategy` 用 `IPIfNonMatch`，目标为域名时先解析再匹配阻断的 IP 段，并加 `full:localhost` 域名规则。
- **原因**：客户端发来的目标通常是域名，只匹配 IP 时通过 `localhost` 或解析到 127.0.0.1 的域名仍可访问 VPS 本机只对内开放的服务（数据库、管理面板等）；符合"安全优先"。
- **代价**：每个新域名多一次 DNS 查询（有缓存），首次访问略增加延迟。
- **否决**：`AsIs`（只拦截直接写成 IP 的目标）。

### D-052 二维码使用 rsc.io/qr；终端绘制方式（由 Claude 决定（用户授权））

- **发现**：M1-07 实机测试中，Xray 正式版 v26.3.27 的 REALITY 服务端与选择 X25519MLKEM768 的目标（microsoft、amazon、samsung 等几乎所有大型网站）握手失败（服务端日志 "handshake did not complete successfully"）；只有仍选择 X25519 的 www.apple.com 可用。在测试 VPS 上逐版本二分：v26.7.28 及之前失败，v26.9.8（预发布版）起成功。
- **内容**：默认安装 / 更新版本 = 最新正式版（若 ≥ v26.9.8），否则不低于 v26.9.8 的最新版本（可能是预发布版）。目标检测同时提供 X25519MLKEM768 和 X25519，记录目标的选择；目标选择 ML-KEM 时，只有 Xray ≥ v26.9.8 才算可用（用户指定旧版本时仍能得到正确判断）。
- **原因**：只用正式版时几乎没有可用的大型目标，节点会"添加成功但连不上"；只在正式版落后时使用预发布版，正式版赶上后自动回到正式版，预发布版的使用范围最小。
- **否决**：只用正式版（几乎无可用目标）；默认总是安装预发布版（不必要的风险）；固定某个预发布版（要人工维护）；不检测 ML-KEM（检测结果与实际不符）。

### D-055 常用目标列表按"从中国大陆实际连通"重新选择（由 Claude 决定（用户授权））

### D-056 客户端管理细节（由 Claude 决定（用户授权））

- **状态**："删除最后一个客户端时连同节点一起删除"已被 D-060 取代；其余不变。

- **内容**：新客户端默认备注 `<节点备注>-<n>`（全局唯一，超过 32 字符时截断节点备注部分）；新客户端沿用该节点已有客户端的流控；删除最后一个客户端时确认后删除整个节点并返回节点列表。

- **否决**：默认备注用随机字符串（难以辨认）；新客户端让用户选择流控（菜单不应暴露组合细节，D-015）。

### D-057 Xray 服务菜单细节（由 Claude 决定（用户授权））

- **内容**：查看日志显示最近 50 行并提示 `journalctl -f` 命令，不在菜单内持续跟踪；未安装时只显示说明；指定低于 v26.9.8 的版本时警告；卸载先删除所有节点（一次多类变更）再删除程序。
- **原因**：持续跟踪需要 Ctrl+C 结束，而 Ctrl+C 在菜单中表示退出 LiteNode（D-030）；先删节点再删程序，保证 ufw 规则清理和 Xray 停止也走变更流程、失败可恢复。
- **否决**：菜单内 `journalctl -f`；未安装时提供"安装 Xray"选项（设计中由添加节点自动安装）。

### D-058 附近网站扫描细节；目标必须返回网页（由 Claude 决定（用户授权））

- **扫描**：以本机公网 IPv4 为中心扫描同一 /24 的 443 端口（并发 10、每个 3 秒）；证书名称去掉通配符和高风险关键词，最多检测 60 个；A 记录在同一 /24 内才算"附近"；按延迟列出前 10 个；首次风险提示确认一次后记住。
- **目标必须返回网页**：所有检测（扫描、常用列表、手动输入）都要求请求 `/` 得到 HTTP 响应（任意状态码）。
- **发现**：测试 VPS 网段中唯一的候选完成 TLS 却不返回网页，像是他人的代理服务器；从中国大陆连接失败。廉价 VPS 网段中这类邻居很常见。
- **原因**：/24 范围小、速度快（约 1 分钟），符合 D-016 的克制要求；A 记录校验排除"证书挂在这里但网站在别处"；不返回网页的主机无法让 REALITY 的回落看起来像真实网站。
- **否决**：扫描更大范围（更慢，更容易被投诉）；接受只完成 TLS 的主机。

### P-001 Xray 安装在独立路径，使用独立服务名

### D-061 sshd 配置读写细节（由 Claude 决定（用户授权））

- **状态**：SSH 设置记在状态文件的 `ssh` 中（端口、密钥登录、密码登录、root 登录策略），每项不写表示不管理；`00-litenode.conf` 由它生成，没有管理项时删除。原因：状态文件是唯一数据源（第 5 节），回滚时状态和配置文件一起恢复；不管理的项保持系统原值，用户只改了一项时不会顺带改变其他设置。新增字段零值即默认，不加 `schema_version`。
- **关闭密码登录同时关闭键盘交互认证**：`KbdInteractiveAuthentication yes` 时 PAM 仍可以让用户输入密码登录，只关 `PasswordAuthentication` 不能真正关闭密码登录。
- **`Include` 检查只看 LiteNode 管理的配置项**：主配置中 `Include` 之前出现管理项或 `Include` 在 `Match` 块中才报错；`HostKey` 等其他配置项不影响结果，不报错，避免误报。
- **应用后用 `sshd -T` 核对**：每次应用（包括恢复后）都核对状态文件中的每一项是否生效，不一致则整体恢复。这样也能发现 `Port` 叠加、其他文件抢先设置等情况。
- **否决**：解析 `00-litenode.conf` 作为数据源（与"状态文件是唯一数据源"冲突）；每次写入全部 4 项（会把用户没改过的系统设置固定下来）；严格要求 `Include` 是主配置第一条有效配置（Debian / Ubuntu 默认配置满足，但商家改过的配置容易误报）。
