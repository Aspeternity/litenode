# 决策记录

记录已经做出的决定、原因和被否决的方案，防止新会话重复讨论或重新提出已否决的方案。

**规则**：

- 只追加，不删除。决定被推翻时，新增一条记录说明，并在旧记录的状态中注明"已被 D-xxx 取代"。
- 状态分为两种：
  - **已确认**：用户已同意，按此实现。
  - **提议**：设计时补充的细节，尚未经用户逐条确认。实现到相关任务时先向用户说明并确认，确认后改为"已确认"。

## 已确认

### D-001 没有 Web 界面，使用数字菜单的命令行工具

- **原因**：目标是轻量，Web 面板常驻占用内存，暴露额外端口也增加风险。菜单风格参考 3x-ui 的命令行菜单。

### D-002 使用 Go 开发，编译为单个二进制文件

- **原因**：零依赖，JSON 处理、二维码、密钥生成都在程序内完成；运行时不常驻，内存占用不是问题；编译 amd64 和 arm64 两个版本即可覆盖绝大多数 VPS。
- **否决**：Bash 脚本。需要 jq、qrencode 等依赖，分享链接、状态文件、SSH 互锁检查等逻辑用 Bash 难以维护。

### D-003 防火墙和端口转发统一使用 nftables

- **原因**：ufw 依赖 Python，精简镜像需额外安装几十 MB；ufw 默认丢弃转发流量，与 nftables 端口转发同时使用需要处理规则冲突。统一用一张 nftables 表更简单、更轻。
- **否决**：ufw。
- **代价**：用户不能用 `ufw` 命令手动管理规则，只能通过菜单或 `nft`。
- **补充**：用户自己在运行 ufw 时，LiteNode 防火墙未启用期间把端口同步到 ufw，见 D-038。本条不变：LiteNode 自己的防火墙和端口转发仍只用 nftables，不安装、不依赖 ufw。

### D-004 不做 fail2ban

- **原因**：依赖 Python 且常驻内存，占用可能超过 Xray；"仅密钥登录 + 修改端口"后暴力破解已无意义。

### D-005 中转只做 nftables 端口转发

- **原因**：链式代理（导入落地机、链式出站、路由规则）在 3x-ui 的 Web 界面中操作更方便，命令行菜单没有优势。纯端口转发零开销，线路机可以不装 Xray。
- **否决**：链式代理出站、出站与路由规则管理。

### D-006 不做快速部署向导

- **原因**：用户认为没有必要。

### D-007 第一版不做流量统计、流量限额、到期停用

- **原因**：需要开启 Xray stats API 并有定时任务持续统计和持久化，增加复杂度。端口转发同样不做流量统计。以后需要时再讨论。

### D-008 不引用 geoip / geosite，没有"更新 geo 数据"功能

- **原因**：Xray 引用 geo 文件时会加载到内存，显著增加占用。节点不需要分流规则，屏蔽内网地址直接写 IP 段。

### D-009 Xray 配置最小化

- **内容**：不开启 stats 和 API，不开启访问日志，只保留 warning 级别日志，出站只有 freedom 和 blackhole。
- **例外**：Reality 回落限速默认开启（见 D-018），它是安全功能且不增加内存占用。

### D-010 第一版只支持 Debian 和 Ubuntu

- **原因**：Alpine 等使用 OpenRC 而不是 systemd，服务管理方式完全不同。核心功能稳定后再考虑。

### D-011 项目名 LiteNode，命令 `litenode` 和 `lnode`

- **原因**：名字表达"轻量"；代理领域没有同名项目（同名项目在 Node.js、Python 等其他领域）。
- **否决**：NodeKit（Algorand 有一个同样是"终端管理节点 + 一行命令安装"的同名工具，容易混淆）；命令名 `node`（与 Node.js 冲突）、`ln`（系统自带命令）、`lnd`（闪电网络常用程序）。

### D-012 开源协议 GPL-3.0

- **原因**：防止被闭源二次打包售卖；与 3x-ui 一致。Xray 是运行时下载的独立程序，其协议不影响本项目。

### D-013 安装方式：一行命令执行 install.sh，从 GitHub Releases 下载程序

- **原因**：与 3x-ui 的安装体验一致，是新 VPS 上最方便的方式。之后可用自己的域名做短链接，程序无需改动。
- **否决**：apt 软件源（首次安装步骤更多）、Docker（守护进程常驻内存）。
- **补充**：之后的更新通过"维护 → 更新脚本"完成。

### D-014 菜单排序和分隔线规则

- **选项顺序**：添加 → 修改 → 启用/禁用 → 其他操作 → 删除和危险操作 → 返回。
- **分隔线**：子菜单的选项区内不加分隔线，唯一的分隔线在 `0. 返回` 上方。删除和危险操作放在最后，但不用分隔线隔开。
- **主菜单例外**：主菜单的分组分隔线已由用户确认保留。
- **原因**：用户明确要求。曾经出现过"分享链接排第二""删除排在中间""在危险操作上方加分隔线"等问题，均被用户否决。

### D-015 节点结构：协议 + 传输 + 安全层，编译时注册

- **原因**：后续要支持纯 VLESS、XHTTP、WS 等多种组合，组合式结构让新增一种传输或协议时所有兼容的组合都能直接使用。菜单只展示预设组合，保持简单。
- **否决**：Go 运行时插件（版本稍有不匹配就无法加载）；每种组合写一个独立类型（组合数量爆炸）。

### D-016 Reality 目标网站：检测必做，扫描为推荐选项

- **内容**：所有选定的目标网站都必须通过 TLS 1.3、H2、X25519、证书检测。提供"扫描附近网站 / 常用列表 / 手动输入"三种方式。
- **扫描限制**：默认只扫同一 /24 网段的 443 端口，低并发，首次使用时提示部分商家禁止扫描。
- **原因**：目标不满足要求时节点连不上；用大站存在 IP 与 SNI 不匹配被识别的风险；同机房的网站更自然。

### D-017 第一版不做"偷自己"

- **原因**：需要域名、证书和 Web 服务，与轻量目标冲突。

### D-018 防止流量偷跑：筛选排除高风险网站 + 默认开启回落限速

- **原因**：Reality 会把未通过验证的连接转发给目标网站，别人可以把 VPS 当作访问目标网站的免费中转。
- **内容**：排除 cdn、download、mirror、video 等关键词的网站；`limitFallbackUpload` / `limitFallbackDownload` 默认采用官方示例值（10MB 后开始限速，1MB/s，突发 5MB/s）。
- **否决**：前置 Nginx 过滤 SNI（需要额外的 Web 服务）。

### D-019 卸载时不回滚 SSH 和防火墙设置

- **原因**：避免卸载后机器恢复成密码登录、端口全开的不安全状态。

### D-020 卸载 Xray 时同时删除所有节点和客户端

- **原因**：卸载后保留节点配置的唯一用途是重装，而重装、换版本、修复已由"更新 Xray（可选指定版本）"覆盖。单独卸载 Xray 的真实场景是落地机改成纯线路机。

### D-021 开发环境：WSL（Ubuntu）+ 测试 VPS（Debian 12），不另建虚拟机

- **内容**：WSL 用于开发、编译、单元测试；测试 VPS 用于验证 SSH、nftables、BBR、swap 和实际连接。测试 VPS 有 VNC 控制台，可随时重装。仓库放在 WSL 主目录，Claude Code 在 WSL 环境中运行。

### D-022 提交和 PR 中不出现 AI 署名

- **内容**：`.claude/settings.json` 中 `attribution.commit` 和 `attribution.pr` 设为空字符串，`CLAUDE.md` 中同时写明规则。

### D-023 暂不配置 GitHub Rulesets

- **状态**：已被 D-036 取代。
- **原因**：单人开发，要求 PR 或检查会增加步骤。用户可以自行添加"禁止删除 main、禁止强制推送"的基础规则。

### D-024 进度衔接方式：仓库内的文档是唯一记忆

- **内容**：`CLAUDE.md`（工作规则）、`docs/DESIGN.md`、`docs/DECISIONS.md`、`docs/ROADMAP.md`、`docs/PROGRESS.md`。任务带编号和验收标准，提交信息带任务编号。
- **分工**：Claude Code（WSL）负责具体实现；claude.ai 对话负责方案指导，新对话时直接读取仓库文件衔接。

### D-025 界面文字集中管理在 `internal/text`

- **内容**：所有用户可见的文字（菜单、提示、确认、错误信息）只写在 `internal/text`，用 Go 函数或常量定义；第一版只有中文，不做运行时语言切换。`fmt.Errorf` 包装的上下文用英文。单元测试扫描其他包的非测试 Go 文件，出现中文字符串即失败（与 `text` 包同时实现）。
- **原因**：为以后支持英文做准备，现在还没有界面文字，集中管理几乎没有迁移成本，事后补做需要改动所有功能代码；同时保证用词统一、逻辑层测试不依赖具体措辞。
- **否决**：JSON / YAML 翻译文件、第三方 i18n 库（失去编译期检查，增加依赖）；文字分散写在各包中（以后支持英文的返工成本最高）。
- **代价**：读代码时需要跳转到 `text` 包才能看到实际文字；每条文字多一处定义。

### D-026 dry-run 只读操作照常执行；操作日志只记录修改操作，1MB 轮转

- **内容**：Runner 区分只读和修改操作，dry-run 下只读操作真实执行、修改操作只打印。`/var/log/litenode.log` 只记录修改操作，超过 1MB 轮转为 `.1`，最多约 2MB。
- **原因**：dry-run 需要基于真实状态才有参考价值；只读查询每次打开菜单都会执行，记录会刷满日志；自行轮转不依赖精简镜像中可能没有的 logrotate。
- **否决**：dry-run 下所有操作都不执行（菜单状态失真）；记录查询操作；交给 logrotate；不控制日志大小。

### D-027 系统检测细节：版本边界、虚拟化显示、共存软件提示

- **状态**："共存软件"一项已被 D-037 取代，其余（版本边界、虚拟化类型显示）不变。
- **版本边界**：下限固定、上限开放（Debian ≥ 11；Ubuntu ≥ 22.04 且为 LTS），拒绝 Ubuntu 非 LTS、Debian testing/sid、衍生发行版。
- **虚拟化类型**：显示在主菜单系统行，如 `Debian 12 | KVM | 512M | BBR ✓`。
- **共存软件**（x-ui/3x-ui、官方 xray、Docker）：按 systemd 单元文件检测，在主菜单状态区下方显示一行警告，不打断操作。x-ui 和 3x-ui 合并显示。
- **原因**：新的 Debian 和 Ubuntu LTS 发布后不需要更新 LiteNode 才能使用；容器环境一眼可见；警告不打断日常使用。
- **否决**：严格版本白名单；虚拟化类型不显示；启动时打印警告并要求按回车；尝试区分 x-ui 和 3x-ui（依赖上游特征，容易失效）。

### D-028 状态文件：字段随任务加入、菜单会话全程持锁、异常时提示不覆盖

- **字段**：M0-04 只做顶层骨架，功能字段在对应任务加入。只有不兼容的改动才加 `schema_version`，v0.1.0 前保持 1。
- **锁**：`flock /run/litenode.lock`，菜单会话全程持有；`internal rollback` 不受锁限制，`internal resolve` 遇锁跳过本轮。
- **异常**：文件损坏或版本比程序新时提示并退出，不自动覆盖、不自动从备份恢复；文件不存在视为首次使用。
- **原因**：一次写全结构容易与后续任务的细化不一致；只在写入时加锁会让两个菜单互相覆盖修改；自动恢复会悄悄丢掉最近的修改。
- **否决**：现在定义完整结构；只在写入状态时加锁；损坏时自动用最近的备份恢复。

### D-029 配置变更流程的实现方式

- **状态**：确认竞态的标记和定时任务"按类型各一个"已被 D-040 取代（改为全局一个，整体回滚一次变更）；其余不变。
- **备份**：每次变更一个目录，原样保存文件 + `state.json` + `manifest.json`，用户可直接复制恢复。
- **校验**：默认在临时位置校验；`sshd` 这类只能校验正式位置的，就地校验、失败立即恢复（服务尚未重载）。
- **确认竞态**：确认和超时回滚通过 rename 认领 `/run/litenode/<类型>.pending` 标记文件，先到者生效；回滚恢复标记中记录的备份 ID，而不是"最新一份"。
- **原因**：与 D-028 中"手动从备份恢复"的提示一致；不必要地改动正式文件越少越好；rename 是原子操作，保证"保留"和"回滚"只发生一个。
- **否决**：JSON 打包备份（无法直接复制恢复）；一律写入后校验；确认时如果已超时仍重新应用新配置（此时已没有回滚保护）。

### D-030 菜单框架细节

- **内容**：选项统一缩进 1 个空格（主菜单示例同步修改）；不清屏；状态区未实现的模块显示 `-`；执行操作时收到 Ctrl+C / SIGHUP / SIGTERM 等操作完成后再退出，等待输入时立即退出。
- **原因**：缩进与状态区、子菜单一致；不清屏可以往上翻看之前的输出；布局从一开始与设计一致；SSH 断开或误按 Ctrl+C 不会让配置停在修改一半的状态。
- **否决**：主菜单 2 格、子菜单 1 格；清屏并要求"按回车继续"；只显示系统行；操作中立即退出。

### D-031 子命令细节

- **内容**：`--dry-run` 要求 root，与正常模式走相同流程；支持 `-v` / `--version` / `-h` / `--help`；`version`、`help` 不需要 root。
- **原因**：dry-run 读到的状态和锁与真实运行一致，预览才可信（在 WSL 中用 `sudo litenode --dry-run`，dry-run 不修改系统）；短写法符合命令行工具习惯。
- **否决**：dry-run 不要求 root（读不到状态文件、拿不到锁，需要大量特殊处理）；只支持 `version` 和 `help`。

### D-032 CI 和发布只用 GitHub 官方 Action + gh CLI；v0.0.1 保留为正式 Release

- **内容**：`actions/checkout`、`actions/setup-go` 按 commit SHA 固定；发布用 `gh release create`，说明取自标签注释。测试标签 `v0.0.1`（开发中测试版）保留为正式 Release。
- **原因**：与"依赖尽量少"的原则一致，固定 SHA 防止 Action 被篡改；install.sh 从 `releases/latest` 下载，预发布版不算 latest，保留 v0.0.1 正好用于 M0-09 在测试机上验证安装。
- **否决**：第三方发布 Action（softprops/action-gh-release、goreleaser）；测试标签标记为预发布版或验收后删除。

### D-033 install.sh 的重复安装和 lnode 冲突

- **内容**：再次运行时用最新版覆盖程序；`lnode` 被其他程序占用时不覆盖，提示后继续。
- **原因**：安装脚本可以兼作"修复/重装程序"，校验失败时旧程序保持不变；不破坏用户已有的其他程序。
- **否决**：已安装时直接进入菜单（程序损坏时无法用安装脚本修复）；`lnode` 冲突时中止安装或覆盖。

### D-034 `/etc/litenode` 下的权限统一显式设置

- **内容**：`/etc/litenode` 711，其下子目录 700、文件 600（包括备份中的 `xray.json` 副本、`nftables.nft`、校验用临时文件），唯一例外是 `/etc/litenode/xray.json` 640 属组 `litenode-xray`。规则集中定义在 `internal/state/layout.go`，所有目录用 `EnsureDir`（创建后显式 chmod），配置变更流程拒绝不符合规则的文件。由测试检查除 `xray.json` 外没有任何文件对 root 以外的用户可读。
- **原因**：用户补充要求（P-002 把 `/etc/litenode` 改为 711 后，不能依赖默认权限，备份里有私钥）。
- **实现中发现**：备份恢复 `xray.json` 时原先会丢失属组，导致 Xray 读不到配置；已在备份中记录属组并在恢复时还原。

### D-035 Xray 安装细节：没有节点时不运行；用集成测试在测试 VPS 上验证

- **补充**：用户手动停止 Xray 的处理见 D-045。
- **内容**：安装只装程序、用户和服务文件，不启动；没有启用的节点时 Xray 停止并取消开机启动。M1-01 的 [VPS] 验收用带 `vps` 构建标签的集成测试（`internal/xray/vps_test.go`）在测试机上执行，正常 `go test` 不包含它。
- **原因**：轻量原则，空跑的 Xray 白占内存；M1-01 没有菜单入口，集成测试不需要为验证增加产品功能。
- **否决**：用空配置一直运行；把 [VPS] 验收推迟到 M1-09。

### D-036 使用分支开发，PR squash 合并，main 受 Ruleset 保护

- **内容**：每个任务一个分支（`<type>/<任务编号>-<英文简述>`），验收通过后开 PR，CI 通过且用户在对话中确认后由 Claude 用 `gh pr merge --squash --delete-branch` 合并。main 用 GitHub Ruleset 保护：必须经过 PR、CI（`test` 任务）通过、禁止强制推送和删除，不要求审批人数，没有绕过名单。仓库只允许 squash 合并，合并后自动删除分支。
- **原因**：install.sh 直接从 main 下载，main 必须始终可用，CI 和测试机验证应在合入 main 之前完成；进行中的提交可以随时推送到远程分支备份；每个任务一个 PR，便于审阅和整体撤回。分支上的操作由 Claude 完成，用户只需确认合并。
- **取代**：D-023（理由"要求 PR 会增加步骤"在改用 PR 后不再成立）。
- **否决**：继续直接提交到 main；一个里程碑一个分支（PR 过大）；merge commit / rebase 合并（main 上提交过多）；用户在网页上合并；只禁止强推和删除、不要求 PR。

### D-037 不按软件名检测共存程序，端口冲突以实际占用为准

- **内容**：删除启动时对 3x-ui、x-ui、官方 xray 的检测和主菜单提示。所有端口冲突检查（节点、转发、SSH、导入）都看系统中实际在监听的端口（读 `/proc/net`，不管是哪个程序，包括只监听 127.0.0.1 的）以及状态文件中登记的端口（包括已禁用的节点和转发，因为 DNAT 不监听端口）；TCP / UDP 分开判断，端口段逐个检查，修改时排除自身，启用已禁用项和导入时也检查。Docker 只在启用 LiteNode 防火墙时提示。

### D-038 ufw 在运行且 LiteNode 防火墙未启用时，把 LiteNode 管理的端口同步到 ufw

- **内容**：节点端口（`ufw allow`）、转发规则（`ufw route allow` 到 DNAT 后的目标 IP 和端口）、SSH 端口（修改端口时）自动同步到 ufw，规则带备注 `litenode:<类型>:<ID>`，只增删带标记的规则。添加前若已有等价的未标记用户规则，则不添加、不打标记、不删除（ufw 判断重复时不看备注，会把用户规则改成带标记）。同步采用整体对账：根据状态文件算出应有规则，与实际带标记规则比较，多删少补；在每次相关变更、转发目标重新解析、导入配置、打开主菜单时进行。SSH 修改端口时先放行新端口，超时回滚后通过对账删除；旧端口的用户规则经用户同意才删除。卸载 Xray 删除节点规则；全部卸载删除节点和转发规则、保留 SSH 规则；卸载脚本保留全部。启用 LiteNode 防火墙时提示先停用 ufw，停用后删除带标记的 ufw 规则；两者同时启用时主菜单警告。firewalld 不同步。
- **与 D-003 的关系**：D-003 决定 LiteNode **自己的**防火墙和端口转发只用 nftables、不依赖 ufw，本条不改变这一点：LiteNode 不安装、不启用、不停用 ufw，nftables 规则照常生成。本条只处理"用户自己在用 ufw"这种共存情况，让 ufw 不挡住 LiteNode 的节点和转发。D-003 的代价"用户不能用 ufw 管理规则"因此只在启用 LiteNode 防火墙后成立。
- **原因**：很多 VPS 用户已经在用 ufw，不同步的话新加的节点和转发会被 ufw 挡住，用户难以排查；只动带标记的规则，不破坏用户已有的配置；整体对账让超时回滚、后启用 ufw、同步中途失败都能自动恢复一致。
- **实现**：通用模块在 M1-07a，节点在 M1-07，SSH 在 M2-05，转发在 M4-01 / M4-02，卸载在 M1-09 / M6-03，导入在 M6-01，与 LiteNode 防火墙的切换在 M3-02。
- **否决**：逐条增删（超时回滚在另一个进程中执行，无法知道要删哪条）；同步 firewalld；自动停用 ufw。

### D-046 端口转发按地址族分别转发

- **内容**：nftables DNAT 不能跨地址族，IPv4 连接只转发到 IPv4 目标、IPv6 连接只转发到 IPv6 目标。目标为 IP 时只转发同一地址族并在列表中标明；目标为域名时分别解析 A / AAAA（`resolved_ipv4` / `resolved_ipv6`，取代原来的 `resolved_ip`），各自转发，ufw 的 `route` 规则也分别生成。存在 IPv6 目标时才开启 IPv6 转发。转发尚未实现，不需要迁移。
- **原因**：两种地址都用时 IPv4 和 IPv6 客户端都能使用，且不需要用户额外选择。
- **否决**：域名只用 IPv4 地址；每条规则由用户选择。

### D-047 x25519 密钥的验收方式；Xray 新特性第一版不做

- **原因**：原验收"格式与 xray x25519 输出一致"在新版本下含义不明；这些新特性是可选增强，现有 VLESS + REALITY 不需要，且许多客户端尚未支持。以后可作为预设或高级选项讨论。

### D-049 Xray 路由阻断内网时也拦截域名

- **内容**：路由 `domainStrategy` 用 `IPIfNonMatch`，目标为域名时先解析再匹配阻断的 IP 段，并加 `full:localhost` 域名规则。
- **原因**：客户端发来的目标通常是域名，只匹配 IP 时通过 `localhost` 或解析到 127.0.0.1 的域名仍可访问 VPS 本机只对内开放的服务（数据库、管理面板等）；符合"安全优先"。
- **代价**：每个新域名多一次 DNS 查询（有缓存），首次访问略增加延迟。
- **否决**：`AsIs`（只拦截直接写成 IP 的目标）。

### D-061 sshd 配置读写细节（由 Claude 决定（用户授权））

- **状态**：SSH 设置记在状态文件的 `ssh` 中（端口、密钥登录、密码登录、root 登录策略），每项不写表示不管理；`00-litenode.conf` 由它生成，没有管理项时删除。原因：状态文件是唯一数据源（第 5 节），回滚时状态和配置文件一起恢复；不管理的项保持系统原值，用户只改了一项时不会顺带改变其他设置。新增字段零值即默认，不加 `schema_version`。
- **关闭密码登录同时关闭键盘交互认证**：`KbdInteractiveAuthentication yes` 时 PAM 仍可以让用户输入密码登录，只关 `PasswordAuthentication` 不能真正关闭密码登录。
- **`Include` 检查只看 LiteNode 管理的配置项**：主配置中 `Include` 之前出现管理项或 `Include` 在 `Match` 块中才报错；`HostKey` 等其他配置项不影响结果，不报错，避免误报。
- **应用后用 `sshd -T` 核对**：每次应用（包括恢复后）都核对状态文件中的每一项是否生效，不一致则整体恢复。这样也能发现 `Port` 叠加、其他文件抢先设置等情况。
- **否决**：解析 `00-litenode.conf` 作为数据源（与"状态文件是唯一数据源"冲突）；每次写入全部 4 项（会把用户没改过的系统设置固定下来）；严格要求 `Include` 是主配置第一条有效配置（Debian / Ubuntu 默认配置满足，但商家改过的配置容易误报）。

### D-062 限时确认在服务器重启后也会回滚；回答"否"立即恢复（由 Claude 决定（用户授权））

- **背景**：DESIGN 第 6 节原有已知限制：等待确认期间服务器重启，临时定时器和 `/run` 下的标记都消失，修改不会被回滚。PROGRESS 记录为在 M2-02 决定。对 SSH 修改来说，这正是最可能把用户锁在外面的情况（例如改坏配置后商家面板重启）。
- **内容**：
  - 待确认标记改放在 `/etc/litenode/rollback/pending`（磁盘上，目录 700）。
  - 第一次限时确认时安装并启用 `litenode-rollback-boot.service`。它是 oneshot 单元，`ConditionPathExists` 指向标记，开机时执行 `litenode internal rollback`，与定时器认领同一个标记、走同一个回滚流程。
  - 用户回答不是 `y` 时立即回滚并停止定时器，不等到超时。
- **原因**：持久化标记加开机单元，改动小，不增加运行时开销：没有待确认修改时，开机单元因条件不满足而跳过。标记不直接放在 `/etc/litenode` 下，因为 `EnsureDir` 会把该目录改为 700，破坏 Xray 需要的 711。
- **验证**：Ubuntu 24.04 测试机在待确认期间重启，开机后配置恢复。实测中还发现，套接字激活的 sshd 在开机时没有 `/run/sshd`，导致 `sshd -T` 无法执行，已改为执行前创建该目录。
- **否决**：
  - 保持已知限制：重启是锁死的常见诱因。
  - 定时器改为持久单元（`Persistent=`）：要写入和删除单元文件、每次 `daemon-reload`，比开机单元复杂。
  - 回答"否"后仍等待超时：用户已确认不可用，没有理由再等。
- **遗留**：卸载 LiteNode（M6）时需要删除该开机单元和 `rollback/` 目录。

### D-063 公钥管理细节（由 Claude 决定（用户授权））

- **`authorized_keys` 走变更流程**（配置类型 `authkeys`）：备份、原子写入、失败恢复，与其他系统文件一致。应用时修正属主和权限，恢复后同样修正。
- **添加不限时确认，删除限时确认**：加公钥不会影响现有登录方式；删除可能删掉当前正用的公钥，按"可能影响 SSH 连接的操作必须限时确认"处理。密码登录关闭时不能删除该用户的最后一个公钥（DESIGN 第 13 节）。
- **只用标准库**：公钥解析、`SHA256` 指纹、ed25519 密钥对和 OpenSSH 私钥格式都自己实现，不引入 `golang.org/x/crypto/ssh`。私钥格式用 `ssh-keygen -y` 在测试机上验证。
- **校验规则**：拒绝 DSA 和小于 2048 位的 RSA（OpenSSH 已不推荐）；粘贴时不接受 `authorized_keys` 选项（少见，且引号解析容易出错），但保留文件中已有的带选项的行。
- **生成的私钥不加密**：只在终端显示一次，用户复制到自己的客户端后可以自行加密码；在服务器上设密码要多一步输入，并且密码会经过服务器。
- **否决**：引入 `golang.org/x/crypto/ssh`（需要第三方依赖，这里只用到很小一部分）；在服务器上调用 `ssh-keygen` 生成（私钥会落盘，即使随后删除）；添加公钥也限时确认（多一步操作，没有安全收益）。

### D-064 登录方式互锁的判断方法（由 Claude 决定（用户授权））

- **P-003 确认**：root 登录设为"禁止"前，要求修改后至少有一个 sudo 用户能登录（有公钥且密钥登录开启，或有可用密码且密码登录开启）。
- **增加总检查**：DESIGN 第 13 节的具体规则之后，再检查修改后 root 或某个 sudo 用户仍能登录。这样能覆盖规则没有列出的情况，例如 root 设为"仅密钥"但 root 没有公钥、也没有 sudo 用户。具体规则先检查，保证提示信息明确。
- **"能登录"的依据**：管理员 = root + `sudo` 组成员（Debian / Ubuntu 的 sudo 组），且有登录 shell；公钥数量来自各自的 `authorized_keys`；密码是否可用来自 `/etc/shadow`；登录设置以 `sshd -T` 的生效值为准。不考虑 `AllowUsers`、`DenyUsers`、`AuthenticationMethods`、`Match` 等少见配置，这些情况由限时确认兜底。
- **否决**：只实现 DESIGN 列出的三条规则（存在规则之外的锁死组合）；把所有可登录的普通用户都算作出路（非 sudo 用户登录后无法恢复 SSH 设置）；检查 `AllowUsers` 等全部 sshd 选项（复杂，收益小，限时确认已经兜底）。

### D-065 修改 SSH 端口：用 ListenAddress 避开 Port 叠加，Ubuntu 按需重启 ssh.socket（由 Claude 决定（用户授权））

- **问题**：`Port` 在 sshd 的所有配置文件中叠加生效。商家在主配置中写的 `Port`（Debian 测试机的 `Port 61234`）会让旧端口继续开放，LiteNode 的核对因此失败（M2-01 实测）。DESIGN 要求不修改主配置。
- **内容**：
  - `00-litenode.conf` 同时写 `ListenAddress 0.0.0.0:N` 和 `[::]:N`（有 IPv6 时）。每个 `ListenAddress` 都带端口时 sshd 忽略 `Port`。
  - 生效端口以 `sshd -T` 的 `listenaddress` 为准，并确认新端口确实在监听。
  - Ubuntu 套接字激活：在 `daemon-reload` 之前读取套接字当前的端口，端口变化时重启 `ssh.socket`，否则只 reload。
  - 改端口时 `ufw` 在 `sshd` 之前应用。
  - 旧端口的用户规则只列出简单规则，经同意才删除，删除不走限时确认：sshd 已不监听旧端口，删除不会影响登录。
- **验证**：
  - Ubuntu 24.04（ufw 运行中）：不确认时 60 秒后恢复到 22，新端口规则被删除；确认后旧的 `22/tcp` 规则经同意删除，新端口可连、旧端口不可连；再改回 22 时规则随之更新。
  - Debian 12：主配置有 `Port 61234` 时改到 2222，只监听 2222，旧端口不可连；改回成功。
- **否决**：
  - 注释掉主配置中的 `Port`：违背"不修改主配置"，而且要用户同意修改设计。
  - 发现其他 `Port` 时拒绝修改，让用户手动处理：对新手不友好，而 `ListenAddress` 能完全避开这个问题。
  - 每次 sshd 变更都重启 `ssh.socket`：没有必要，只在端口变化时重启。
  - 在 `daemon-reload` 之后读取套接字端口：实测读到的已是新配置，会漏掉重启。

### D-066 创建 sudo 用户（由 Claude 决定（用户授权））

- **内容**：
  - 加入 `sudo` 组，用 `chpasswd` 从标准输入设置密码。为此 Runner 新增 `ExecInput`，输入不记录日志。
  - 密码由用户输入或自动生成 16 位（去掉易混淆字符，约 93 位熵），只显示一次。
  - 可以复制 root 的公钥。
  - sudo 需要密码。
  - 不走限时确认，失败时删除已创建的用户。
- **原因**：
  - 用公钥登录的 sudo 用户也需要密码才能使用 sudo。
  - 免密 sudo 会让公钥泄露直接等于 root 权限。
  - 把密码放在命令行（`usermod -p` 或 `chpasswd` 的参数）会被 `ps` 和操作日志看到。
- **否决**：
  - 免密 sudo（NOPASSWD）。
  - 只用公钥、不设密码：无法使用 sudo。
  - 自己实现 SHA-512 crypt 再 `usermod -p`：代码多，而且哈希会出现在命令行。

### D-067 SSH 菜单细节和"回滚到上次修改前"的范围（由 Claude 决定（用户授权））

- **公钥列表**：root 和 sudo 用户的公钥放在同一个编号列表中，多个管理员时显示用户名。添加和生成时只有 root 就不问用户。原因：大多数 VPS 只有 root；有 sudo 用户时，管理员也需要看到并管理他们的公钥。
- **回滚范围**：只恢复最近一次 sshd 修改之前的 SSH 设置（状态中的 `ssh`），以 ufw + sshd 的变更、限时确认的方式应用。原因：备份中的完整状态会撤销之后的节点修改。回滚本身也是一次修改，再执行一次会回到回滚前，行为可以预期。回滚不做互锁检查：之前的设置当时是可用的，而且有限时确认兜底。
- **sudo 用户的密码输入**：手动输入时用终端 `ioctl` 关闭回显（标准库 `syscall`），输入两次。自动生成是推荐项。
- **主菜单 SSH 状态**：`<端口> / 仅密钥|仅密码|密钥+密码`。
- **否决**：
  - 按用户分组显示并分别编号：删除时需要两步选择。
  - 回滚时恢复备份中的整个状态。
  - 用 `stty` 外部命令控制回显：要启动进程，标准输入不是终端时还会输出报错。

### D-070 nftables 表结构和基础规则（由 Claude 决定（用户授权））

- **内容**：
  - 一个文件 `/etc/litenode/nftables.nft`，开头 `table inet litenode` + `delete table inet litenode`，加载时在一个事务中替换整张表；不需要表时只保留这两行，等于删除表。
  - input 链 `policy drop`，始终放行：已建立 / 相关连接（丢弃 invalid）、回环、ICMPv6 邻居发现和路由器报文（`nd-neighbor-solicit/advert`、`nd-router-solicit/advert`、`mld-listener-query`）、DHCP 回复（`udp sport 67 dport 68`）、DHCPv6 回复（`fe80::/10` 的 `udp 547 → 546`）。
  - ping 开关只影响 `echo-request`。
  - 每条放行规则带注释 `litenode:<所有者>`（`ssh`、`node:<ID>`、`manual:<ID>`、以后的 `forward:<ID>`），供"检查并修复"对比。
  - 有来源限制时 IPv4、IPv6 分成两条规则。`tcp+udp` 用 `meta l4proto { tcp, udp } th dport`。
  - 状态文件 `firewall`：`enabled`、`block_ping`、`rules`（手动规则）、`auto_sources`（自动规则的来源限制，按所有者保存，随端口变化保留，P-004）。自动规则本身不保存，由 SSH、节点、转发生成。
  - SSH 端口：状态中管理了端口时用它（将要切换到的端口），否则用 `sshd -T` 的实际端口。
  - `litenode-nft.service` 仿照 Debian 的 `nftables.service`（`DefaultDependencies=no`，在 `network-pre.target` 之前加载），只在有表时启用，不修改 `/etc/nftables.conf`。
- **原因**：
  - 测试机 Ubuntu 的 IPv6 路由来自路由器通告，挡掉就会断网。
  - 使用 DHCP 的 VPS 挡掉 DHCP 回复后，租约到期会失去地址（ufw 默认也放行这两项）。
  - 数据包要经过所有 input 钩子链，Debian 自带的 `table inet filter`（全部 accept）不影响 LiteNode 的过滤。
- **否决**：
  - 逐条增删规则：无法原子替换，失败时难以恢复。
  - 修改 `/etc/nftables.conf`：会和用户或系统自己的配置混在一起。
  - 用一条规则同时写 IPv4、IPv6 来源：nft 的 `ip saddr` 和 `ip6 saddr` 不能写在同一个集合里。

- **否决**：关闭时清空手动规则（误操作代价高）；重置保留 ping 设置；没有 nft 时报错让用户自己安装（菜单项本来就叫"安装并启用"）。

### D-073 防火墙规则管理的细节（由 Claude 决定（用户授权））

- **内容**：
  - P-004 按原提议确认：自动规则（SSH、节点、转发）在防火墙菜单中只能设置来源 IP 限制，删除时提示到对应菜单修改。
  - 放行端口依次询问：端口（单个或 `起始-结束` 范围）、协议（TCP + UDP / TCP / UDP）、来源 IP（逗号或空格分隔，地址或网段，留空为任意来源）、备注。已有相同端口和协议的手动规则时，选完协议立即拒绝并提示用"修改规则"。来源 IP 保存前去重、去掉被其他网段包含的地址并排序。
  - 修改规则：手动规则进入子菜单，可分别改端口、协议、来源 IP、备注；自动规则子菜单只有来源 IP。
  - **限时确认的范围**：修改前后"哪些规则以 TCP 放行 SSH 端口、各自的来源限制"不同时走限时确认（例如限制 SSH 的来源、删除或修改覆盖 SSH 端口的手动规则），其余操作（放行其他端口、ping 开关、节点端口的来源限制）直接应用，仍走备份 → 校验 → 应用 → 失败恢复。检查并修复会重写整张表，始终走限时确认。
  - **检查并修复**：读取 `nft list chain inet litenode input`，按注释中的所有者分组，与状态生成的规则逐条比较，报告缺少、多余、不一致的规则，以及基础规则（默认策略、ping、ICMPv6 等）不一致、表未加载。比较按含义而不是文本：nft 会重排集合元素、单元素集合不写花括号、合并重叠或相邻的网段（如 `1.2.3.4, 1.2.3.5` 显示为 `1.2.3.4/31`，Debian 12 实测），所以来源按地址范围比较。
- **原因**：每次放行端口都要限时确认太繁琐，而只增加放行不会切断 SSH；以"SSH 端口的可访问性是否改变"为准，比按操作类型列举更不容易漏掉（例如一个覆盖 SSH 端口的端口范围）。文本比较会因 nft 的格式化误报。
- **否决**：所有修改都走限时确认；检查并修复用 `nft -j` 解析 JSON（结构复杂，收益小）；按文本比较规则。

### D-074 防火墙与节点、SSH 联动的实现（由 Claude 决定（用户授权））

- **内容**：
  - 新增变更类别 `firewall`（`firewall.SyncKind`），不带文件：应用时读取磁盘上的状态，防火墙已启用时生成 `nftables.nft`，先 `nft -c` 校验，内容有变化才原子写入并加载；未启用时什么都不做。与 ufw 类别一样，失败恢复后再次应用即按恢复后的状态重新生成。
  - 节点的全部变更（添加、改端口、启用 / 禁用、删除、客户端变更）由 `xray`、`ufw`、`firewall` 三类组成一次变更；卸载 Xray 时 Xray 已不存在，也以 `ufw` + `firewall` 变更删除节点规则。
  - SSH 改端口和"回滚到上次修改前"的顺序为 `ufw` → `sshd` → `firewall`：防火墙在 sshd 重新加载之后生成，SSH 端口以状态或 `sshd -T` 的实际值为准，回滚到"未管理端口"时也能放行 sshd 实际使用的端口。限时确认超时或回答 n 时，规则随状态恢复。
  - `ssh` 包不能引用 `firewall`（`firewall` 引用 `ssh`），由 `app` 把 `firewall.SyncKind` 注入 `ssh.Service.Firewall`；回滚子命令的类别表中登记 `firewall`。
- **原因**：沿用变更流程，节点或 SSH 变更失败、超时回滚时防火墙规则自动一致；防火墙放在 sshd 之后，不需要预测 sshd 新端口，sshd 重新加载到防火墙加载之间只有毫秒级间隔，已建立的连接不受影响。
- **否决**：由调用方预先生成 `nftables.nft` 作为 `nft` 类别的文件（SSH 回滚到未管理端口时无法预知 sshd 端口）；防火墙放在 sshd 之前并同时放行新旧端口（确认后还要再清理一次旧端口）。

### D-075 端口转发规则和内核转发的实现（由 Claude 决定（用户授权））

- **内容**：
  - **规则结构**：prerouting 每个地址族一条 DNAT（`meta nfproto ipv4|ipv6` 限定地址族）；postrouting 按"原始目的端口"做 masquerade（`ct original proto-dst <本机端口> ct status dnat masquerade`）；防火墙启用时 forward 链默认丢弃，放行已建立的连接和 `ct original proto-dst <本机端口> ct status dnat` 的转发流量。本机端口由端口冲突检查保证唯一，所以按原始端口匹配只会命中 LiteNode 自己的转发。
  - **端口段**：目标端口段与本机端口段相同时 DNAT 不写端口（保持原端口）；不同时用 `dport map` 一一对应。nft 的 `dnat to 地址:端口段` 是从段中任选端口，不是按偏移对应，不能用。
  - **来源限制**：转发规则的自动来源限制（`auto_sources` 中的 `forward:<ID>`）只在防火墙启用时生效，写在 forward 链的放行规则上；DNAT 规则本身不带来源限制。转发规则不写入 input 链（DNAT 后流量不经过 input），也不算作 SSH 访问。
  - **表的生成**：`firewall.SyncKind` 改为无论防火墙是否启用都按状态生成整张表（防火墙关闭时只有转发链）；从来没有表且没有转发时不创建文件。转发的变更由 `sysctl`、`firewall`、`ufw` 三类组成一次变更（D-040），先开内核转发再加载规则。
  - **内核转发**：新增 `sysctl` 类别管理 `/etc/sysctl.d/99-litenode.conf`（M5 的系统优化也写这个文件）：有启用的 IPv4 目标时 `net.ipv4.ip_forward = 1`，有启用的 IPv6 目标时 `net.ipv6.conf.all.forwarding = 1`。不再需要时从文件中删除（没有设置时删除文件），但不把运行中的值改回 0：Docker、VPN 等可能依赖转发。
  - **IPv6 路由器通告**：开启 IPv6 转发后，`accept_ra = 1` 的网卡会忽略路由器通告，靠 SLAAC 获得的地址和默认路由会在过期后丢失。因此开启 IPv6 转发时，把当前 `accept_ra = 1` 的网卡（不含 `all`、`default`、`lo`）在同一文件中先设为 `2`；已经写进文件的网卡以后仍保留。
  - **ufw**：`route allow` 规则支持端口段（`port 40000:40010`）；多条转发指向同一目标时只保留第一条的备注，避免对账时来回改写备注。
  - **其他**：转发备注可以为空，不为空时格式同节点备注，不要求唯一；添加时没有 `nft` 就先安装 nftables（与启用防火墙相同）；删除转发时一并删除它的来源限制；添加 / 修改时解析域名（A 和 AAAA 分别解析，当前使用的地址仍在解析结果中时保持不变），定时重新解析在 M4-02。
- **原因**：按原始端口匹配，规则数量与转发数量成正比，与目标地址无关，域名重新解析时 postrouting 和 forward 链不变；`dport map` 是 nft 中唯一可靠的端口一一映射写法；`accept_ra` 问题会让 IPv6 机器在开启转发后数小时内断网，且不易察觉。
- **否决**：按 DNAT 后的目标地址和端口做 masquerade（会影响本机或 Docker 发往同一目标的流量，且地址变化时要改多处）；DNAT 规则上加来源限制（防火墙关闭时来源限制也会生效，与节点规则不一致）；删除最后一条转发时把 `ip_forward` 改回 0（可能中断其他软件）；不处理 `accept_ra`。

### D-076 域名目标定时重新解析的实现（由 Claude 决定（用户授权））

- **内容**：
  - **timer**：`litenode-resolve.service`（oneshot，`ExecStart=<程序路径> internal resolve`）和 `litenode-resolve.timer`（`OnCalendar=*:0/5`、`AccuracySec=10s`），写在 `/etc/systemd/system/`。每次转发变更成功后同步：有域名目标（含已禁用的规则）时写入单元并 `enable --now`，没有时 `disable --now` 并删除单元文件；`internal resolve` 未发现变化时也同步一次，修复缺失或多余的 timer。
  - **timer 失败不回滚转发**：转发变更已经生效后 timer 设置失败，返回 `TimerError`，提示"规则已更新，但定时任务设置失败"，不回滚规则。
  - **重新解析**（`forward.Reresolve`）：A / AAAA 分别比较；当前地址仍在结果中时不变；记录不存在（`DNSError.IsNotFound` 或 Go 解析器对缺少该类记录返回的 `no suitable address found`）时该类地址清空；查询失败（超时、服务器错误）时保留该类当前地址；两类都没有时保留原地址并记录错误。每个域名查询限时 15 秒。已禁用的规则也重新解析，启用时使用最新地址。
  - **执行**：需要 root；`flock` 非阻塞取实例锁，取不到时输出"跳过本轮"并以 0 退出，持锁期间运行，避免菜单同时启动修改状态。有变化时按转发的多类变更（sysctl + firewall + ufw）应用，ufw 对账随之完成；未变化时不写任何文件、不创建备份。结果输出到 journal：更新的规则、查询失败（退出码 0）、应用失败（退出码 1）。
- **原因**：`OnCalendar` 间隔固定，不受单次运行时长影响，满足"5 分钟内更新"；DNS 临时故障时清空地址会删除仍可用的规则，保留旧地址的代价只是延后一轮；已禁用的规则保持 timer 和地址，避免启用时用到过期 IP；timer 是辅助功能，失败时回滚已经可用的转发规则得不偿失。
- **否决**：`OnUnitActiveSec=5min`（加上默认 1 分钟精度可能超过 5 分钟）；查询失败时清空地址；只在有启用的域名规则时保留 timer；把 timer 纳入变更流程一起回滚；锁被占用时等待（timer 运行可能堆积，且菜单会话可能持锁很久）。

### D-077 端口转发菜单的细节（由 Claude 决定（用户授权））

- **内容**：
  - **列表**：列为 ID（序号）、本机端口、协议（`tcp` / `udp` / `tcp+udp`）、目标、状态、备注。只有一个地址族可用的目标（IP 目标、只有一类记录的域名）在目标后标"仅 IPv4" / "仅 IPv6"（D-046）。设计示例没有备注列，备注为空时这一列空着。
  - **添加 / 修改**：同一个 5 步流程：本机端口 → 协议 → 目标地址 → 目标端口（默认与本机端口相同） → 备注。修改时每一步以当前值为默认（回车保留），协议选择标出"(当前)"；什么都没改时不应用。端口冲突在选完协议后检查（冲突与协议有关），冲突时列出原因并回到第 1 步；目标端口段长度与本机端口段不同时重新输入。
  - **测试目标连通性**：从本机对规则实际使用的每个地址（IPv4、IPv6；域名用已解析的地址）的第一个目标端口发起 TCP 连接，每个地址限时 5 秒，显示连通和延迟或失败原因；端口段只测第一个端口并说明；`udp` 规则只提示无法测试，`tcp+udp` 只测 TCP 并说明。
  - **timer 失败**：规则已生效但 `litenode-resolve.timer` 设置失败（D-076）时，流程按成功结束，下方单独警告。
- **原因**：修改涉及端口段长度联动（本机端口段和目标端口段必须等长），逐项修改的页面需要额外处理联动，带默认值的流程更简单且一次能改全；检查规则实际使用的地址才能反映 DNAT 后的连通性。
- **否决**：像修改节点那样做成逐项修改的页面（端口段联动复杂）；连通性测试时重新解析域名（与规则实际使用的地址可能不同）；在端口这一步就检查冲突（此时还不知道协议）。

### D-078 BBR + fq 的实现（由 Claude 决定（用户授权））

- **内容**：
  - **状态**：新增 `sysopt.bbr`。`99-litenode.conf` 由状态整体生成（`sysctl.Desired`，BBR 两行在内核转发之前），端口转发变更时也会保留 BBR。
  - **状态显示**以运行中的 `tcp_congestion_control` 为准；菜单项按情况开启、关闭（只在由 LiteNode 开启时），或提示"已由系统的其他配置开启"。
  - **关闭**：从文件删除两行后执行 `sysctl -w net.ipv4.tcp_congestion_control=cubic`（D-122 改为系统配置中的值）；`default_qdisc` 不改回（只影响之后创建的网卡队列，重启后由系统默认值决定）。
  - **立即生效**只执行 `sysctl -p`，不对已有网卡执行 `tc qdisc replace`：BBR 从 Linux 4.13 起自带 pacing，不依赖 fq；重启后网卡使用 fq。
  - 内核在设置 `bbr` 时自动加载 `tcp_bbr` 模块，不写 `/etc/modules-load.d/`（实测 Ubuntu 24.04 重启后保持，模块此前由其他配置加载的情况已排除）。
- **原因**：sysctl 文件由多个功能共用，只有从状态生成才能保证转发和 BBR 互不覆盖；以运行值显示能反映服务商镜像自带的设置（两台测试机都由镜像开启了 BBR）。
- **否决**：只提供开启不提供关闭；关闭时 `sysctl --system`（会重新应用用户的所有 sysctl 文件，影响范围过大）；对已有网卡立即替换为 fq（可能短暂影响连接，收益很小）。

### D-079 swap 的实现（由 Claude 决定（用户授权））

- **内容**：
  - **文件**：`/litenode.swap`，一眼可见由 LiteNode 创建；系统已有的 swap（分区、服务商的 `/swapfile`）只在菜单中列出，不修改。没有状态字段，状态从 `/proc/swaps` 和 `/etc/fstab` 读取。
  - **创建**：先 `fallocate`（失败则删除后用 `dd`），chmod 600，`mkswap`，然后以 `swap` 类型的变更写入 `/etc/fstab`（只增删第一列为 `/litenode.swap` 的行，其他行原样保留）。`swap` 类型的应用步骤按 fstab 实际情况行事：有这一行则 `swapon`，没有则 `swapoff` 并删除文件，所以失败恢复 fstab 后会顺带清理新建的文件。
  - **调整大小**：先建好新文件 `/litenode.swap.new`，再 `swapoff` 旧文件、改名、`swapon`；新文件建不出来时旧 swap 不受影响。fstab 不变。
  - **删除**：以变更删除 fstab 中的行，应用步骤 `swapoff` 并删除文件。
  - **限制**：128M ~ 32G；创建后磁盘至少保留 256M（调整时新旧文件同时存在，按当前剩余空间计算）。停用（调整、删除）前要求 swap 已用量小于可用内存减 64M，否则拒绝，避免触发 OOM。
  - **可用性探测**：有 `/proc/swaps` 且不是容器（LXC、OpenVZ 中 `swapon` 会被拒绝）。不实际试建 swap 文件。
  - **建议大小**：内存小于 1G 时建议 1G 并作为默认值；否则默认 1G，不显示建议。大小可输入 `512`、`512M`、`1G`、`1.5G`。
- **原因**：固定且专用的文件名避免误改用户的 swap；fstab 是用户文件，只按第一列精确匹配自己的行；先建后换能在磁盘或内存不足时保住原 swap。
- **否决**：使用 `/swapfile`（常被服务商或用户占用）；在状态文件中记录大小（与系统实际情况可能不一致）；先删旧文件再建新文件（失败时没有 swap）；实际执行 `swapon` 测试探测能力（会修改系统）。

### D-080 IPv4 / IPv6 优先级的实现（由 Claude 决定（用户授权））

- **内容**：
  - `/etc/gai.conf` 中只管理带 `# BEGIN LiteNode: prefer IPv4 (managed by LiteNode)` 和 `# END LiteNode` 标记的一段，内容为 `precedence ::ffff:0:0/96  100`；优先 IPv6 = 删除这一段（glibc 默认）。修改走变更流程（`gai` 类型，无校验、无应用步骤：glibc 发现文件变化后自动重新读取）。文件原本不存在、删除后为空时删除文件。
  - **状态**从文件读取（不进状态文件）：段内或段外存在未注释的 `precedence ::ffff:0:0/96 N`（N > 40，即高于 IPv6 默认优先级）即为优先 IPv4。段外的行（用户自己写的）不修改，切换为优先 IPv6 后仍优先 IPv4 时提示手动修改。
  - **已知限制**：Xray 和其他 Go 程序使用 Go 自己的解析器，不读取 `gai.conf`，节点出站不受此设置影响。如需让 Xray 出站也按此优先，需要在 Xray 配置中设置 `domainStrategy`，属于设计变更，待用户决定。
- **原因**：标记段可以精确增删而不碰用户的其他配置；从文件读取状态能反映用户手动修改的情况。
- **否决**：整体覆盖 `gai.conf`（丢失用户配置）；注释掉用户自己的 precedence 行；用 sysctl 关闭 IPv6 实现"优先 IPv4"（会让 IPv6 节点和转发失效）。

### D-081 DNS 设置的实现（由 Claude 决定（用户授权））

- **内容**：
  - **判断是否使用 systemd-resolved**：服务在运行，且 `/etc/resolv.conf` 的内容是 systemd-resolved 生成的（含 `systemd-resolved` 字样，stub 或上游列表两种模式都算）。服务在运行但 resolv.conf 不指向它时按"不使用"处理，因为程序实际读取的是 resolv.conf。
  - **systemd-resolved**：写 `/etc/systemd/resolved.conf.d/litenode.conf`（`DNS=...`、`Domains=~.`），应用步骤重启 systemd-resolved。`Domains=~.` 让全局 DNS 用于所有域名，优先于 DHCP 下发到网卡的 DNS。"恢复系统默认"删除该文件。
  - **resolv.conf**：整体重写为 LiteNode 的 nameserver，保留原有的 `search`、`domain`、`options` 行；原来是符号链接（如 resolvconf）时替换为普通文件。不提供"恢复系统默认"（没有可靠的默认内容，用户可以选择其他 DNS）。
  - **变更流程**：`dns` 类型，失败自动恢复。
  - **测试**：应用前用 Go 解析器直接向每个服务器（UDP 53）查询 `www.cloudflare.com`，限时 3 秒，失败时列出并询问是否仍要使用（默认否）；应用后 `getent hosts` 测试系统解析，失败只提示。
  - 当前 DNS 显示：LiteNode 设置的值，或系统的值（`resolvectl dns` / resolv.conf 中的 nameserver）。DNS 不进状态文件。
- **原因**：两种模式都按系统实际使用的文件修改才会生效；事先测试服务器可以避免填错 IP 让系统无法解析。
- **否决**：在 resolvconf 的 `head` 文件中追加（DHCP 的 DNS 仍在后面，结果不确定）；用 `chattr +i` 锁住 resolv.conf（影响系统工具，用户难以排查）；在 resolved 下修改 `/etc/systemd/resolved.conf` 本身（覆盖用户配置）；应用后解析失败就自动回滚（可能只是暂时网络问题）。

### D-082 时区与时间同步的实现（由 Claude 决定（用户授权））

- **内容**：
  - 状态读取 `timedatectl show -p Timezone -p NTP -p NTPSynchronized -p CanNTP`；读取失败（部分容器没有 systemd-timedated）时整项隐藏。不进状态文件，也不走变更流程（没有 LiteNode 生成的文件，用户可随时改回）。
  - **时区**：常用 10 个（UTC、上海、香港、台北、东京、新加坡、洛杉矶、纽约、伦敦、柏林）加手动输入，按 `timedatectl list-timezones` 校验后 `timedatectl set-timezone`。
  - **时间同步**：`CanNTP=no`（Debian 12 精简镜像没有任何 NTP 服务）时先 `apt-get install -y systemd-timesyncd`，再 `systemctl try-restart systemd-timedated`（实测：正在运行的 timedated 保留启动时的 NTP 服务列表，不重启则 `set-ntp` 报 "NTP not supported"），然后 `timedatectl set-ntp true`；已装 chrony / ntp 时由 `set-ntp` 使用它们，不另装。开启后每 2 秒检查一次，最多 30 秒，未同步只提示稍后查看。
  - 容器中隐藏"开启时间同步"，状态区不显示同步标记。
- **原因**：`timedatectl` 是 Debian / Ubuntu 的统一接口，能同时适配 timesyncd 和 chrony；安装 timesyncd 只在没有任何同步服务时进行，避免与用户的 chrony 冲突。
- **否决**：直接 `systemctl enable --now systemd-timesyncd`（与已有的 chrony 冲突）；用 `ntpdate` 一次性校时（不持续同步）；时区列表全部列出（四百多项，不便选择）。

### D-083 系统优化菜单的细节（由 Claude 决定（用户授权））

- **内容**：状态行按 DESIGN 第 15 节的顺序（BBR、swap、优先、时区）显示，字段间三个空格；swap 显示所有 swap 的总大小（包括非 LiteNode 创建的），没有为"无"。不可用的项隐藏时状态行中对应的字段也省略，并显示一行提示（含虚拟化类型）。各项的状态在每次显示菜单时重新读取系统，不进状态文件（BBR 除外，见 D-078）。主菜单的 BBR 标记也在每次显示时重新读取。菜单渲染用 golden file 测试（`internal/app/testdata/sysopt_menu.golden`）。
- **原因**：状态以系统实际情况为准，用户在别处修改后也能正确显示；隐藏的功能在状态行出现会让人误以为可以设置。
- **否决**：状态行显示不可用的字段并标"不可用"；把各项设置都记录到状态文件（与系统实际情况可能不一致）。

### D-084 节点出站 IP 与系统优先级分开设置（用户同意）

- **内容**：IPv4 / IPv6 的选择分成两个互相独立的设置：系统优化中的"系统 IPv4 / IPv6 优先级"（`gai.conf`，只有优先 IPv4 / 优先 IPv6，影响 curl、apt 等）；Xray 服务菜单中的"节点出站 IP"（freedom 出站 `domainStrategy`：AsIs / UseIPv4v6 / UseIPv6v4 / ForceIPv4 / ForceIPv6，存 `xray.outbound_ip`）。选"仅"前检查本机有对应的公网地址和默认路由。新任务 M5-07。
- **原因**：两者需求常常相反，例如落地机的 IPv6 很纯净，节点要仅 IPv6 出站，而系统工具需要 IPv4 才能访问 GitHub；Xray 和 Go 程序本来就不读 `gai.conf`（D-080）。
- **否决**：一个设置同时作用于两处（无法满足上述场景）；整个移到 Xray 菜单（线路机不装 Xray 时系统优先级无处设置）；系统侧提供"仅"选项（`gai.conf` 只能调整顺序）。
- **提议**：以后可在"修改节点"中为单个节点覆盖全局设置（生成多个出站并按入站分流），需要时再做。

### D-085 节点出站 IP 的实现细节（由 Claude 决定（用户授权））

- **内容**：状态值用 `""` / `prefer_ipv4` / `prefer_ipv6` / `ipv4_only` / `ipv6_only`，默认不写 freedom 的 `settings`。"仅"模式的检查：`ip route show default` 有该协议的默认路由，且 `ip -o addr show scope global` 有该协议的地址；IPv4 允许私有地址（NAT VPS 常见），IPv6 要求非 ULA、非文档地址。菜单项放在"查看日志"之后、"更新 Xray"之前（第 5 项），状态区单独一行显示模式。
- **原因**：可读的状态值便于导出文件和手工排查；NAT VPS 的 IPv4 出站正常，只看公网地址会误拒；IPv6 通常不做 NAT，只有 ULA 时无法出站。
- **否决**：直接存 Xray 的 `domainStrategy` 字符串（与 Xray 版本耦合）；"仅"模式前实际发起一次外网连接测试（慢，且出口受防火墙或网站影响，误判多）；IPv4 也要求公网地址（误拒 NAT VPS）。

### D-086 导出文件的格式与导入的细节（由 Claude 决定（用户授权））

- **内容**：导出文件是状态文件的子集（`format: "litenode-export"`、`schema_version` 与状态文件相同、`litenode_version`、`exported_at`、`nodes`、`forwards`、`firewall`），所以状态文件的迁移函数同样用于导出文件。`firewall` 只含手动规则、`block_ping` 和节点 / 转发的来源限制；不含防火墙开关和 SSH 的来源限制。也不导出节点出站 IP（`xray.outbound_ip`）、Xray 版本和手动停止标记。默认导出到 `/root/litenode-export-<时间>.json`，可修改路径。导入保留原 ID，`next_id` 取两者较大值；导入前完整校验（Reality 密钥对、UUID、备注、端口、转发、规则、ID 和端口不重复）；端口冲突只算本机其他程序（当前节点的 Xray 端口不算，它们会被替换）。导入是一次 sysctl + xray + firewall + ufw 的多类变更，LiteNode 防火墙启用且改变了 SSH 的可达性时走限时确认；之后同步转发的重新解析定时器。
- **原因**：与状态文件同格式，迁移只写一份；防火墙开关、SSH 来源限制和出站 IP 都与机器本身有关（新机器可能没有 IPv6，开启防火墙要走单独的检查流程）；保留 ID 让来源限制等引用不错乱。
- **否决**：自定义导出格式（迁移要维护两套）；导入时一并开启防火墙（可能断开 SSH，且跳过了启用前的检查）；重新分配 ID（要同时改写来源限制的引用）；导入时询问是否合并（P-005 已定为替换）。

### D-087 更新脚本的细节（由 Claude 决定（用户授权））

### D-088 卸载的细节（由 Claude 决定（用户授权））

- **内容**：
  - 卸载脚本：删除 `litenode`、`litenode.bak` 和指向 litenode 的 `lnode`（其他程序的 `lnode` 不动）；先更新转发的重新解析服务，它带 `ConditionPathExists=<程序路径>`，程序不在时跳过运行（转发保留现有地址）。
  - 全部卸载：两次确认；先把删除所有节点和转发作为一次多类变更（sysctl + xray + firewall + ufw），然后删除重新解析定时器、ufw 中 `litenode:node:` / `litenode:forward:` 规则（ufw 未启用时也删除）、Xray、`litenode-rollback-boot.service`，防火墙未启用时删除 `nftables.nft` 和 `litenode-nft.service`，再删除 `/etc/litenode`（防火墙启用时保留其中的 `nftables.nft`）和程序。来源限制中只保留 SSH 的。Xray 程序已被外部删除时跳过 Xray 的配置校验，照样卸载。

  - 第一步变更失败时什么都没删除，照常报错返回菜单；之后的步骤失败时继续执行其余步骤，最后报告错误并退出。

### D-092 Xray 启动 / 停止的状态判断与实时日志（由 Claude 决定（用户授权），2026-10-19，M7-02）

- **Runner 增加 `Stream`**：只读命令、输出直接写到终端、dry-run 下也执行，与 `Query` 一致。

### D-097 按回车返回菜单的实现（由 Claude 决定（用户授权），2026-10-19，M7-06）（"普通的一行说明不停"已由 D-128 修改）

- **由操作显式标记**：`ui.Session.Hold()` 由显示了内容的操作调用，`Run` 在操作结束后（流程已关闭）显示"按回车返回菜单"；动作返回错误（`ErrBack`、`ErrQuit` 除外）时自动停住；以警告结束的流程（`└─ ⚠ ……`，如导入文件不存在、限时确认超时已恢复）用 `Session.EndWarn` 结束，同样停住——清屏后这类一行的错误会立即消失，页面上也看不出发生了什么。普通的一行说明（如"Xray 已在运行"）不停。否决：根据流程结束后是否还有输出自动判断（二维码、实时日志直接写输出流，流程内的测试结果在 `└─` 之前，判断不可靠）。
- **只在终端中停住**：标准输入和标准输出都是终端时才停住。理由：停住是为了下一步清屏（M7-07）时不冲掉内容，管道输入不清屏也没人看；脚本和 golden 测试不用多输入空行。否决：始终停住。
- **实时日志按 Ctrl+C 结束后也停住**：清屏后最后几行日志仍可看完再返回。
- **不停住的**：防火墙"检查并修复规则"（问题列在确认修复之前，用户已经停下来读过）、只问一个值的设置、卸载（卸载后直接退出 LiteNode，输出留在屏幕上）。

### D-098 页面清屏与路径标题的实现（由 Claude 决定（用户授权），2026-10-19，M7-07）

- **在 `ui.Session.Run` 中统一实现**：`Run` 维护页面名称的栈，在流程外显示的菜单就是页面，标题线写成 `主菜单 › … › 页面名`（主菜单在路径中叫"主菜单"，仍用大框标题）；各页面的构建函数不需要知道自己从哪里进入。否决：每个页面自己写完整路径（同一页面可能从不同位置进入，如以后加的快捷入口，也容易漏改）。
- **清屏条件与 M7-06 的停住共用 `Session.Interactive`**（标准输入和输出都是终端）。理由：标准输入是管道而输出是终端时没有人按回车，清屏会冲掉还没读的内容。否决：只看标准输出（D-096 原文），与停住的条件不一致时会丢内容。
- **每次显示页面都清屏**，包括页面中一个操作结束后重新显示：一行的结果（如"✓ 已启用"）随之清掉，结果反映在页面状态区；需要阅读的内容和错误已由 D-097 停住。否决：操作后不清屏（新页面和上一屏的流程挤在一起，正是 D-096 要解决的问题）。
- **只清当前屏幕**（`ESC[H ESC[2J`），不发 `ESC[3J`：往上翻仍能找到之前的输出。

### D-100 修改密码与删除 sudo 用户的实现（由 Claude 决定（用户授权），2026-10-19，M7-09）

- **恢复旧密码哈希**：新增配置类型 `password`，文件 `/etc/litenode/password-restore` 记录要恢复的 `用户名:哈希`，应用时用 `chpasswd -e`（经标准输入）设置与 `/etc/shadow` 不同的哈希，然后删除文件。修改前写入旧哈希，再以内容不变的变更走限时确认（备份即旧哈希），回滚安排好之后才执行 `chpasswd`。这样超时、选择恢复、开机回滚都沿用现有的变更流程，只改回这一个用户。否决：把 `/etc/shadow` 整个作为变更文件（需要自己算新哈希，Go 标准库没有 yescrypt；恢复时会覆盖这段时间内其他用户的修改）；`usermod -p` 恢复（哈希出现在命令行）；先改密码再安排回滚（中间出错时没有回滚）。
- **修改密码的对象**：root 和能登录的 sudo 用户（与密钥管理的用户范围相同）。自动生成的密码在限时确认之前显示一次，否则用户无法用新密码测试登录。
- **删除 sudo 用户**：`userdel --remove`，主目录和邮件一并删除（用户由 LiteNode 用 `--create-home` 创建，留下主目录会把公钥等文件留在磁盘上；确认提示写明不能恢复）。不能删除 root；用 `pgrep -u` 发现该用户有进程（正在登录，包括通过 sudo 运行 LiteNode 的会话）时拒绝，提示先退出；不使用 `--force`。删除前按当前生效的登录策略检查 root 或其他 sudo 用户仍能登录。不走限时确认：删除不可撤销，安全性靠删除前的检查。否决：保留主目录（留下无主文件，以后同 UID 的新用户会拿到它们）；再问一次是否删除主目录（多一步，绝大多数情况都应删除）。
- **SSH 状态区的 sudo 用户数**：只计能登录的 sudo 用户（与互锁检查的范围相同）。

### D-107 VLESS Encryption 节点的参数（由 Claude 决定（用户授权），2026-10-19）

- **认证方式 X25519**，否决 ML-KEM-768：ML-KEM-768 的客户端密钥 1184 字节，链接约 1700 个字符，终端二维码远超 65 列（DESIGN 9.5）；密钥交换本身已是 X25519 + ML-KEM-768 混合，后量子安全不受影响。
- **native 外观**，否决 xorpub / random：经中转的落地机不需要进一步混淆；native + TCP 时 Vision 仍可 splice，CPU 开销最低。
- **服务端票据 600s、客户端 0rtt**：与 `xray vlessenc` 的默认输出一致。不提供填充等高级选项，保持菜单简单。
- **流控 Vision**：与 encryption 搭配是 Xray 推荐用法。
- **默认端口随机**（10000～60000 的空闲端口），否决默认 443：没有伪装 HTTPS 的需要，443 留给 Reality 节点。
- **备注 `Enc-<端口>`**，与 `Reality-<端口>` 对应。
- 详细设计见 DESIGN 第 9.7 节。

### D-115 连通性检测的计数规则与状态判断细节（由 Claude 决定（用户授权），2026-10-19，M10-01）

- **规则**：用具名计数器（`arrive_tcp`、`pass_tcp`……），`nft -j list table` 直接读出计数，不必解析规则表达式。来源集合按协议和地址族分开（`src_tcp4`、`src_udp6`……，`size 5`、`flags dynamic`），每个协议的来源单独列出。计数和"加入集合"分成两条规则：集合满时 `add @set` 会结束所在规则，计数不能受影响。规则用 `nft -f -` 从标准输入加载，脚本开头先建再删表，残留的表被一次事务替换。Debian 11（nft 0.9.8）和 Debian 13（nft 1.1.3）实测语法和 JSON 一致，集合元素同时兼容纯字符串和 `{"elem": {"val": ...}}` 两种形式。
- **中间状态**：DESIGN 的三种状态之外加"检测中"（有包到达但还不满足"通"或"本机拦截"的条件），界面显示用。用户按回车或到 30 分钟上限时，"检测中"的协议按当前计数归类：有包通过算"通"，没有算"本机拦截"。"本机拦截"之后又有包通过时回到"检测中"，自动结束的 2 秒等待重新计算。
- **结论**：本机拦截时 ufw 运行和 LiteNode 防火墙启用两种提示都可能出现（两者同时开着时都列出）；都没有时才检查其他入站规则（D-044），检测结果可能为空，此时仍提示"系统中其他入站规则"。TCP 有包（通或拦截）而 UDP 没有包时给"只有 UDP 未到达"的结论；TCP 也没有包时 UDP 与 TCP 给相同的"未到达"结论。
- **菜单（M10-02 补充）**：Ctrl+C 取消检测、不给结论（与"查看实时日志"相同，D-090，回到菜单）；按回车或自动结束才给结论。显示块在终端中用光标上移原地重绘，期间关闭输入回显，免得回车打乱位置；结束时擦掉"按回车结束检测"一行。结论中每个协议列出到达 / 通过包数和最多 5 个来源，"来源中可能包含扫描器"只在最后显示一次。程序被强制结束（SIGKILL）时临时表留下，下次启动时在取得实例锁之后删除。
- **ufw 提示**：LiteNode 每次打开菜单都会同步 ufw 规则（D-038），被删掉的带 `litenode:` 备注的规则会自动补回，所以 ufw 拦截多半是用户自己的 deny 规则或检测期间改了规则；提示改为"缺少时重新打开 LiteNode 或禁用再启用节点会重新同步；同时检查有没有拦截该端口的 deny 规则"。
- **否决**：用规则注释区分计数（JSON 中要逐条解析表达式，旧版 nft 格式不同）；所有协议共用一个来源集合（经线路机时 TCP 和 UDP 来源可能不同，分开更有用）；写临时文件再 `nft -f`（多一个要清理的文件）。

### D-118 Hysteria2 的 Xray 字段、证书写法与数据结构（由 Claude 决定（用户授权），2026-10-20，M11-01）

- **实测**（Debian 12 / 11，Xray v26.10.17）：入站 `protocol: "hysteria"` + `settings.version: 2`、`clients[].auth/email`；`streamSettings.network: "hysteria"`、`hysteriaSettings.version: 2`、`security: "tls"`（ALPN 由传输层自动设为 h3）。v26.3.27 是第一个有 hysteria **入站**的版本（v26.2.6 只有出站，v25.10.15 不认识 `hysteria` 传输），即节点的最低 Xray 版本。Xray 出站用 `pinnedPeerCertSha256`（证书 SHA-256，十六进制）固定指纹：匹配叶证书时不再检查名称；指纹错误时连接失败。另一台机器经 Xray 出站连通 TCP 和 UDP（列出客户端时自动开启 UDP 中继）。
- **Brutal**：Xray 服务端只有设置了 `finalmask.quicParams.brutalUp` 才用 Brutal，否则不论客户端声明多少带宽，服务端发送（线路机下载方向）都用 BBR。第一版不写 `quicParams`，即服务端 BBR；线路机出站声明的 `up` 只影响线路机的发送方向。不加带宽菜单（与 D-117 一致）。
- **证书写进 Xray 配置**：`tlsSettings.certificates[].certificate / key` 用行数组内联，不另写证书文件。`xray.json` 本来就是 `0640 root:litenode-xray`，已含 REALITY 私钥，权限相同；证书随配置一起原子写入、备份和回滚，没有文件和配置不一致的问题。否决：写 `/etc/litenode/certs/*.pem` 并在配置中引用（多一类文件要管理权限、原子更新和回滚，没有收益）。因此 M11-02 不需要"证书文件写入"。
- **证书内容**：ECDSA P-256，CN 和 SAN 都是 `www.bing.com`，有效期从生成前 1 天到 10 年后，序列号 128 位随机，私钥 PKCS #8。名称不验证（指纹固定），`www.bing.com` 是自签 Hysteria2 证书的常见写法，握手中的 SNI 不显眼，也不带任何能识别 LiteNode 的字符串。第一版不提供修改。否决：每个节点随机名称（SNI 本身显得异常）、`litenode`（可被主动探测识别）。
- **数据结构**：协议、传输都叫 `hysteria`（与 Xray 一致，显示名 Hysteria2），安全层 `tls`，节点的 `tls` 字段保存 `server_name`、`certificate`、`key`（PEM），以后 TLS 类节点可以复用。客户端密码放在客户端的 `key` 字段（与 SS2022 用户密钥同一字段），32 位小写十六进制（16 字节，链接中无需编码）。`Node.UsesTCP()` 对 hysteria 为假，`PortProto()` 为 `udp`，端口冲突、ufw、防火墙、连通性检测因此只看 UDP。导入备份时检查证书能解析、与私钥匹配、名称不为空，密码格式正确。
- **指纹的两种形式**：证书 SHA-256（十六进制，Xray / Hysteria 链接 `pinSHA256` / mihomo）和公钥（SPKI）SHA-256（base64，sing-box），测试向量取自 openssl。
- **预设**到 M11-02 再注册（加入添加节点菜单），M11-01 合并后菜单不出现未完成的类型。

### D-122 关闭 BBR 时恢复系统配置中的拥塞控制（由 Claude 决定（用户授权），2026-10-20，FIX-01）

- **内容**：关闭 BBR 时，删除 `99-litenode.conf` 中的两行后，按 systemd-sysctl 启动时的规则算出其他 sysctl 文件给 `net.ipv4.tcp_congestion_control` 的值（`sysctl.BootValue`）：读取 `/etc/sysctl.d`、`/run/sysctl.d`、`/usr/local/lib/sysctl.d`、`/usr/lib/sysctl.d`、`/lib/sysctl.d` 中的 `*.conf`，同名文件以前面的目录为准，按文件名排序，最后一次设置生效。`/etc/sysctl.conf` 经 Debian / Ubuntu 自带的 `/etc/sysctl.d/99-sysctl.conf` 链接读到。只在运行值不同时执行 `sysctl -w` 设为该值，没有文件设置时设为 cubic。结果为 bbr 时提示 BBR 由哪个文件保持开启、如需关闭请修改该文件。`default_qdisc` 仍不改回（D-078）。

### D-123 sysctl 文件改名为 99-zz-litenode.conf（用户 2026-10-20 同意，FIX-02）

- **内容**：LiteNode 的 sysctl 文件从 `/etc/sysctl.d/99-litenode.conf` 改为 `99-zz-litenode.conf`。开机时 systemd-sysctl 按文件名顺序读取、最后的值生效，旧名排在 `99-sysctl.conf`（Debian / Ubuntu 指向 `/etc/sysctl.conf` 的链接）之前，`/etc/sysctl.conf` 中的同名设置（如加固脚本写的 `ip_forward = 0`）会在重启后覆盖 LiteNode 的设置，转发静默失效。改名后 LiteNode 的设置开机时最后生效，与运行时一致。
- **迁移**：每次启动（取得锁、读取状态后）若旧文件存在，原子改名为新文件；内容不变，不需要重新加载。两个文件都存在（改名中断）时以新文件为准，删除旧文件。改名失败只显示警告，不影响使用。
- **原因**：用户在 LiteNode 中明确开启转发或 BBR，应以 LiteNode 的设置为准；改名能自动解决，成本低。
- **否决**：不改名只在写入后检查并提示被哪个文件覆盖（只能提醒，用户仍需手动修改）；只在下次修改 sysctl 设置时迁移（不修改设置的已有安装一直保留问题）；`zz-litenode.conf` 等不以数字开头的名字（与 sysctl.d 惯例不一致）。名字更靠后的文件（如 `zz-*.conf`）仍可能覆盖，很少见，不处理。

### D-126 粘贴公钥与改登录方式时设置密码（用户 2026-10-23 同意方向，细节由 Claude 决定（用户授权），FIX-04）

- **内容**：
  - 粘贴公钥：只在这个提示期间开启 bracketed paste、关闭 ECHOCTL，仍用终端的行模式读取，标记之间的多行合并；没有标记时，终端上 300 毫秒内连续到达的行算同一次粘贴（不支持 bracketed paste 的终端粘贴多行时，不会把后面的行当作菜单输入），并先显示类型、指纹、注释再确认，默认"否"。
  - 多行拼成一行：依次尝试不加空格、在一处断行加空格、在两处加空格，取第一个能解析的；同时 `ParseKey` 要求公钥数据恰好是该类型的字段（与 sshd 一致，ed25519 1 个、ecdsa / rsa / sk-ed25519 2 个、sk-ecdsa 3 个），否则注释接在数据后面的错误拼法可能被当作有效公钥。
  - 私钥：内容含 `PRIVATE KEY` 或 `PuTTY-User-Key-File` 时整段丢弃并提示。
  - 改为"仅密码"/"密钥 + 密码"：只列出按当前 root 策略能用密码登录的管理员（root 登录为"仅密钥"或"禁止"时给 root 设密码不能用于 SSH 登录），一个都没有时跳过密码步骤（由互锁检查决定能否修改）。新密码计入互锁检查后先 `chpasswd`、不进入回滚，再改 SSH 设置限时确认。
- **原因**：粘贴时换行直接提交、折行的公钥无法识别、误贴私钥后剩余的行被当作后续输入；开启密码登录时没有设置密码的入口，容易开启后无人能用密码登录。行模式加标记合并改动最小，不需要自己实现行编辑。
- **否决**：进入原始模式自己实现行编辑（工作量大，退格、中文输入等都要处理）；查询终端是否支持 bracketed paste（没有可靠的查询方法）；多行一律用空格或一律不用空格拼接（断行位置不确定）；密码修改也进入回滚（用户要求只回滚 SSH 设置；SSH 设置恢复后新密码仍可用于 sudo 和控制台）。

### D-127 系统优化：BBR 已由其他配置开启时停住，✗ 改为红色（由 Claude 决定（用户授权），2026-10-25，FIX-05）

### D-128 所有"无需操作"的一行说明都停住（用户 2026-10-25 要求统一修复，细节由 Claude 决定（用户授权），FIX-06，修改 D-097）

### D-129 M12 纯 IPv6 支持（用户 2026-10-27 同意，修改 D-042、D-085、D-102）

- **背景**：用户在纯 IPv6 VPS（Debian 13）手动安装后发现很多问题。实测：GitHub 没有 IPv6，安装 / 更新失败；商家 DNS 前两个是不可达的 IPv4 服务器，每次解析 6～12 秒，Reality 检测（5 秒含解析）全部超时；节点出站"仅 / 优先 IPv4"使节点完全不通；按 README 开启 WARP 后，共享出口被 GitHub API 匿名限流（60 次/小时）返回 403，Xray 装不上，且查不到默认版本使常用列表的 ML-KEM 目标全部被拒；WARP 出口被设为默认分享地址并误报 NAT 机。四种节点、防火墙、限时回滚、SSH 改端口、连通性检测、IPv6 转发在纯 IPv6 下正常。
- **内容**：新增阶段 M12（任务见 ROADMAP）：下载不用 GitHub API；出口检测与 WARP 识别；没有 IPv4 出口时经 NAT64 下载；WARP 管理；各处检查与提示；README。
- **修改 D-085**：出口检测实际连一次外网（`1.1.1.1:443` 等，3 秒，每次运行最多一次、按需）。原否决理由是慢和误判；纯 IPv6 机器有内网 IPv4 和默认路由，只看路由会误判且后果是节点不通，而检测结果只用于提示和确认（只有"仅 IPv4"会被拒绝）。
- **修改 D-042**：NAT64 只做 IP 层转换，TLS 直接与 github.com 建立，内容无法被篡改，与被否决的下载代理不同。商家 NAT64 自动使用；公共 NAT64 先询问用户（默认否），且先确认服务条款允许内置，否则只在 README 介绍。
- **修改 D-102**：程序识别 WARP（trace 中 `warp=on`），不再只靠 README 提醒。
- **WARP 实现**：`wireguard-tools` + 内核 WireGuard，密钥与注册用 Go 标准库，无第三方程序或库；只补缺少的协议；放在系统优化第 6 项。
- **否决**：Cloudflare 官方 WARP 客户端（常驻内存几十 MB、软件源支持不确定、默认接管全部流量可能影响 SSH）；只在 Xray 内用 WireGuard 出站连 WARP（下载仍不通，两套方案）；扫描附近 IPv6 网站（网段太大）；默认使用公共 NAT64 不询问。
